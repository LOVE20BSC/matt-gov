# 四阶段与轮次模型

Type: grilling
Status: resolved
Blocked by:

## Question

锁定投票、行动、验证、铸币四阶段的区块区间和轮次映射。明确“铸币第 N 轮/验证第 N+1 轮/行动第 N+2 轮/投票第 N+3 轮”的规范表达；定义投票阶段首个推举者如何测量上一轮实际区块数、平均窗口和异常阈值；确定目标自然日、默认阶段区块数的调整公式、生效轮次、阶段起始区块/阶段区块数历史记录，以及 APY 使用的时间基准。

## Comments

用户确认：公共时间线合约应按其维护和校准阶段数据的职责命名为 `LOVE20Phase`；`Round` 保留为轮次概念和查询结果，不作为合约名。

## Answer

公共合约命名为 `LOVE20Phase`。

- `LOVE20Phase` 是四阶段共用的阶段时间线，维护每个阶段的 `startBlock`、`phaseBlocks`、同步观测数据和动态校准，并提供按阶段查询当前轮次及历史阶段信息。
- `Round` 是时间线上的业务编号，从 `1` 开始；`0` 只表示未设置的存储值。它不是公共合约的职责名称。
- 阶段合约通过 `LOVE20Phase` 获取轮次和阶段边界，不再各自维护独立轮次状态。
- 下一阶段的 `phaseBlocks` 使用生成该阶段记录时已生效的默认值；上一阶段只决定下一阶段的 `startBlock`。
- 四阶段仍按固定错开关系运行：`Mint N`、`Verify N+1`、`Action N+2`、`Vote N+3`。四个阶段同时处于运行中，不表示串行执行顺序。
- 空轮次不逐个写入存储；已记录的阶段直接查询，未记录部分按最近历史锚点计算。
- 动态校准由任何人可调用的幂等 `sync()` 执行；投票阶段首个推举治理者在推举时负责自动调用。校准使用最近三个有效阶段，允许范围为目标自然日的 `±25%`，连续同向超出才调整；新值只按最近有效阶段的实际观测计算。
- APY 不进入合约，由前端按部署时设定的目标自然日计算。
