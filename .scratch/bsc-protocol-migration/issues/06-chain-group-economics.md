# 链群行动与服务者激励

Type: grilling
Status: resolved
Blocked by: 01, 02, 03

## Question

定义链群行动中参与者、公共验证者、链群服务者三类角色的边界；服务者候选与分成、验证结果到服务激励的映射、gas 补偿来源和上限；二次分配达到 100% 时的溢出/舍入保护；服务者和验证者的撤销、替换、结算以及治理监督规则。

## Comments

> 本节保留了旧版实现事实和历史命名；实现只以本票据 `Answer` 及地图 `Decisions so far` 为准。

从旧 `extension-group` 代码核对出的事实：链群服务激励由独立的服务行动合约铸造，旧实现再按链群行动铸币量计算链群 owner 理论份额（旧函数名为 `generatedActionRewardByVerifier`，但其参数实际是链群 owner），并允许链群 owner 为每个行动/链群配置二次分配地址和比例。旧实现的分配对象是钱包地址，BSC 版应改为 `MemberNFT` / `memberId` 或链群 NFT（`groupId`）主体；当前控制地址只负责调用和收款。

已确认的 BSC 规则：

- 公共验证者激励从链群服务 Proposal 的激励中分配，不从链群行动 Proposal 的激励中扣除；竞选在链群行动执行合约中完成，链群服务 Proposal 由其 Proposal Target 铸造后再分配。
- 链群服务沿用旧版业务范围：一个服务 Proposal 面向整个 `actionTokenAddress` 代币社区的全部链群行动，不绑定单个源 `actionId`。服务 Proposal 的激励代币与被服务的行动代币可以不同，典型关系是父币激励子币社区；创建 KV 除保留的 `executor` 项外，传入旧版业务参数 `actionTokenAddress` 和 `govRatioMultiplier`，`ActionTarget` 只透传、不解析这些业务字段。
- 公共验证者必须完成全部链群快照验证；验证不完整时，底层 Proposal 激励仍可由 Proposal Target 铸造，链群行动执行合约取得后可以按业务规则销毁该笔激励，但链群行动、行动者、链群服务、公共验证者和链群 owner 的行动层分配全部为 `0`。
- 完整验证时，先按各完整验证行动的行动激励权重分摊链群服务激励，再对每个行动按其候选申请冻结比例 `r` 分给该行动的公共验证者，剩余部分按链群服务规则分配给链群 owner；比例统一使用 `1e18` 精度。

建议的最小二次分配保护：服务行动执行合约一次性取得本轮服务激励，先按完整验证行动的行动激励权重分摊各行动预算，再扣除各行动公共验证者份额，最后按每个链群的配置比例向接收主体分配。比例总和允许等于 `1e18`；各项金额向下取整，累计分配不得超过对应行动预算，舍入余数归链群 owner。这样 100% 分配是合法输入，不会因 `预算 - 已分配` 出现下溢；链群 owner 可为零份额。

用户确认：链群服务不包含 gas 补偿逻辑，不设置相关接收对象、金额、比例或上限。

用户修正：链群服务业务逻辑沿用旧版，服务 Proposal 面向整个 `actionTokenAddress` 代币社区的链群行动集合，不绑定单个源 `actionId`。旧版工厂创建服务实例只是部署方式；新版本取消工厂，不改变聚合范围、激励公式或按链群/行动配置接收主体的业务语义。

用户补充确认：链群服务加入只接受两类 `MemberNFT`：目标 `actionTokenAddress` 社区中有效链群的 owner，或相关链群行动中拥有有效公共验证者竞选申请的候选人。加入资格不依赖某一轮是否已经选出公共验证者；服务激励计算和铸造时仍必须逐个考虑被服务行动本轮的公共验证者状态。

旧版遗留问题已定位：`ExtensionGroupService._calculateReward` 先对服务者铸币量占比向下取整，再计算服务者理论激励；`_scaledGroupRewardWithContext` 又按单个链群份额单独向下取整。两处分母不一致时，单链群理论激励之和可能大于服务者的 `mintReward`。当该链群二次分配比例为 100% 时，`_claimReward` 的 `mintReward - distributed` 发生下溢，整个链群服务激励铸造交易回滚，表现为“激励无法铸造”。最小整数复现（精度取 1000）：服务激励 `S=3`、行动激励总量 `T=3`、服务者份额 `G=2`、单链群份额 `g=2`，旧公式得到 `mintReward=1`、`groupReward=2`。

## Answer

- **角色边界**：链群 `MemberNFT`（`groupId`）是链群服务者主体，当前持有人只是调用和收款地址；公共验证者也是链群行动执行合约按本轮竞选锁定的 `MemberNFT`。链群服务激励属于独立的链群服务提案执行合约，不属于底层治理合约或链群行动激励。
- **加入资格**：服务加入时只接受两类 `MemberNFT`：在该 `actionTokenAddress` 社区中存在有效链群的 owner，或在相关链群行动中存在有效公共验证者竞选申请的候选人。两类资格满足其一即可加入，不要求该轮已有公共验证者；加入成功不承诺本轮一定产生服务激励。未加入服务的 owner 或候选人不参与服务层激励铸造。
- **激励流向**：仅关联的链群服务行动执行合约可发起调用 `ActionTarget` 铸造 Proposal 激励；`ActionTarget` 作为 Proposal Target 调用 `Mint`，由 `Mint` 将激励铸给 `ActionTarget` 并返回实际数量，`ActionTarget` 在同一笔交易中将全部数量转回该链群服务行动执行合约；执行合约再负责后续分配。服务激励聚合时逐个检查被服务链群行动本轮是否存在已锁定的公共验证者且已完成全部快照验证：先按完整验证行动的行动激励权重分摊服务激励预算，再按该行动冻结比例 `r` 将其预算分给公共验证者，余款按服务行动规则分配给链群 owner 及其配置的接收主体；无公共验证者或验证不完整时，该链群行动不计入行动层分配。底层 Proposal 激励仍可铸造，链群行动执行合约可以按业务规则销毁该笔激励。
- **二次分配**：分配比例统一使用 `1e18` 精度，单个链群的比例总和不得超过 `1e18`，允许正好 100%。各接收金额向下取整，累计分配不得超过该链群预算，舍入余数归链群 owner；不得通过减法产生下溢，100% 分配时 owner 金额为 `0`。
- **旧版舍入溢出修复**：BSC 版使用同一组未提前截断的分子/分母计算各完整验证行动的服务预算、公共验证者份额和 owner 理论份额（实现使用 `Math.mulDiv` 或等价的全精度计算）。每个行动先按其行动激励占完整验证行动激励总量的比例取得服务预算，再按该行动的 `r` 切出公共验证者预算，余款才进入 owner 分配；累计可铸造金额必须受服务 Proposal 实际 `mintReward` 上限约束，100% 二次分配不得回滚。
- **回归验收**：必须覆盖上述最小复现、单链群 100% 分配、多链群累计舍入和治理上限下的分配；断言服务者铸造成功、所有转账总和不超过 `mintReward`、`remaining` 不下溢，且历史重复铸造保护仍有效。
- **状态与监督**：链群激活、退出、服务者变更、接收主体配置和历史结算由链群服务行动执行合约自行记录，并按 `rewardTokenAddress + serviceActionId + 本层 Round` 隔离；被服务行动的数据按 `actionTokenAddress + sourceActionId + 本层 Round` 读取。链群 `MemberNFT` 转移只改变当前控制者，不改变 `groupId` 历史归属。公共验证者的候选变更、首个提交锁定、监督和完整性规则遵循[公共验证者竞选与验证](03-public-verifier-election.md)，不在服务激励合约中重复实现。
- **服务范围与旧版参数**：服务 Proposal 的激励代币记为 `rewardTokenAddress`（即 Proposal 的 `tokenAddress`），被服务的整个链群行动社区记为 `actionTokenAddress`；不绑定单个源 `actionId`。首版允许同币服务，也允许父币激励子币，沿用旧版的父子代币关系校验。服务创建 KV 只需保留旧版业务参数 `actionTokenAddress` 和 `govRatioMultiplier`；`GROUP_ACTION_FACTORY_ADDRESS`、`GROUP_RECIPIENTS_ADDRESS` 等属于部署依赖，不作为用户初始化参数。
- **聚合与铸造闭环**：服务执行合约按 `actionTokenAddress + 治理轮次 + executor` 从 `ActionTarget` 读取该执行合约关联的 `proposalId[]`；该查询内部从 `Vote` 读取本轮有投票 Proposal ID，再逐个读取执行合约映射并筛选，不依赖独立反向索引。随后按核心治理投票占比门槛筛出可铸造 Proposal 激励的行动，过滤掉无公共验证者或未完成全部快照验证的行动，对剩余行动先按行动激励权重分摊服务 Proposal 预算，再按各自冻结比例 `r` 分给公共验证者，余款按 owner 规则聚合 `totalActionReward` 与 `generatedActionRewardByOwner`。`ActionTarget` 不计算投票门槛，也不在 `proposalId[]` 查询返回值中重复携带 `executor`。核心的行动激励投票门槛必须大于零，因此每轮达到门槛的行动数量有上限；不再通过业务工厂枚举。服务参与登记也沿用旧版：`MemberNFT` 只要在该 `actionTokenAddress` 社区的任一链群行动中有有效链群即可加入服务，服务加入量汇总整个社区的链群激活质押。链群行动的候选分割线属于行动执行合约；链群 owner 的接收主体和比例按链群、行动、服务轮次动态配置，不属于服务全局初始化。仅服务执行合约可铸造该服务 Proposal；未完成的行动份额不产生行动层分配，具体销毁规则沿用链群行动激励规则。
- **部署与扩展边界**：链群服务作为提案扩展由 `ActionTarget` 创建和关联，不按每个行动部署业务工厂；执行合约自行解析其创建 KV、验证结果和分配配置。链群服务没有 gas 补偿能力。
