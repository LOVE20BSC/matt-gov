# 公共验证者竞选与验证

Type: grilling
Status: resolved
Blocked by: 01, 02

## Question

定义每轮公共验证者候选资格、申请说明和分成比例；撤销/修改申请时清空已有投票的精确定义；治理投票排名与验证开始区块的映射；首个提交者如何锁定本轮行动验证资格；验证如何分批提交、重复提交和失败处理；治理者如何监督实际验证者，以及验证奖励如何结算。

## Comments

用户确认：公共验证者候选资格限定为目标代币社区中拥有有效治理权的 `LOVE20Member`；申请以 `memberId` 记录，不使用裸地址，不额外要求 SL/ST 或押金。

用户补充确认：公共验证者竞选发生在链群行动的行动执行合约中；验证者激励不从链群行动激励中扣除，而是铸造到链群服务行动的行动执行合约，再由链群服务行动执行合约负责分配。

用户确认：所有比例分配统一使用 `1e18` 精度，比例取值范围为 `0` 到 `1e18`，不使用基点单位。

用户确认：候选申请只在投票阶段内可新增、撤销或修改；撤销或修改立即清空该成员本轮已有投票。投票阶段结束后，当前轮候选名单、排名和分成比例冻结，后续修改只影响下一轮。

用户曾确认固定前 3 名的验证资格；该规则现修订为由初始化时传入的验证阶段分割线数组决定，保留第 1 名在验证阶段开始时可提交、首个有效提交永久锁定且不设置失效或接管的约束。

用户确认：验证者必须完成当轮全部链群的验证才能获得激励；若验证不完整，该链群行动及其关联的行动者、链群服务、公共验证者和链群主均没有激励。这里的全有或全无范围不扩展到底层独立的治理激励。

用户同意：完整验证时，最终验证者从链群服务激励总额中按申请时冻结的比例 `r` 获得 `总额 × r`，其余 `总额 × (1 - r)` 按链群原有服务激励规则分配给链群主；比例统一使用 `1e18` 精度。

用户确认：可验证候选人的数量作为链群行动执行合约的初始化参数，以验证阶段分割线数组表达。第 1 名默认在验证阶段开始（`0%`）可提交；数组有 `n` 个严格递增分割线时，排名前 `n + 1` 名可以验证。例如 `[0.5e18, 0.75e18]` 表示前 3 名可以验证。

用户确认：验证阶段分割线数组允许为空；每个分割线必须满足 `0 < split < 1e18`，并且数组严格递增。候选人的开放区块按本轮验证阶段起始区块与阶段区块数计算，不使用验证阶段结束后的区块。

用户确认：本轮验证集合是行动阶段结束时至少有一个成员参与的链群快照；空链群不计入，验证阶段开始后链群停用、恢复或新增不改变集合。快照参考现有按轮次历史记录的实现，并允许分批推进，避免单笔交易遍历全部行动者而受 Gas 限制。

用户确认：每个链群按本轮成员历史顺序维护批量验证游标，`startIndex` 必须等于已验证数量，批次连续且不可重复或跳过；首个有效批次的公共验证者锁定整轮，之后只能由同一 `memberId` 继续提交，全部快照链群完成才算本轮完成。

用户确认：旧版链群行动合约中的 `verifierByGroupId` 实际记录的是链群 NFT owner，不是公共验证者；新模型应改用链群 owner 语义记录链群归属，并另行记录本轮实际锁定并提交验证的公共验证者。

用户修正：这里的链群 owner 指链群 NFT 主体本身，不是钱包地址；链群 NFT 在激活时就已确定，转移只改变控制者，不改变 `groupId` 身份和历史归属。验证集合快照只用于确定本轮有参与者的链群 NFT，不用于确定 owner；旧版代理验证者逻辑一并删除。

用户确认：本轮锁定的是公共验证者 `memberId`，不是钱包地址；后续每个批次都要求调用者是该 `MemberNFT` 当前持有人。`MemberNFT` 转移后由新持有人继续完成本轮验证，不支持代理验证者，锁定的 `memberId` 在本轮不变。

用户确认：删除不信任投票及其理由、扣分和历史重算逻辑。治理者在投票阶段给行动投票的同时，为公共验证者候选人投票；上一轮发现验证问题时，下一轮不再给该候选人投票，以此完成监督，不对上一轮奖励做回溯扣除。

用户曾确认回调失败不回滚核心投票；该规则现修正为回调失败时回滚整笔投票交易。`LOVE20Vote` 不解析或理解任何行动执行合约业务，只把投票附带的 KV 数组原样交给执行合约处理；行动执行合约相关的校验和业务错误由回滚暴露。

用户确认：投票没有 KV 数组时不触发行动执行合约回调；只有附带非空 KV 数组时才调用最小回调入口。

用户修正：多行动批量投票继续支持，每个 `actionId` 都可以附带独立的 KV 数组；某个行动没有 KV 时只跳过该行动的回调。通用回调只传递 `tokenAddress`、`round`、`actionId` 和不透明 KV，不传 `voter`、`memberId`、`votes` 等特定执行合约字段；执行合约需要这些信息时自行从 KV 解析。

用户补充确认：BSC 版协议中，除明确的技术性特殊情况外，所有业务参与主体统一使用 `MemberNFT`，不再以钱包地址作为主体身份。

用户确认：公共验证者、候选投票、验证集合和链群 owner 均属于链群行动执行层；链群服务激励及其分配属于链群服务行动执行层，不属于底层 `Stake`、`Submit`、`Vote`、`Mint`。底层 `Vote` 只提供逐提案 KV 传输和回调机制，不理解这些业务。

用户补充：底层投票对象统一称为 `Proposal`，通用回调的定位使用 `proposalId`；行动类提案经 `LOVE20Action` 初始化成功后，该 `proposalId` 才作为有效 `actionId` 使用。

## Answer

- **候选资格与资料**：候选人必须是目标代币社区中拥有有效治理权的 `MemberNFT`，以 `memberId` 记录；不要求 SL/ST 或额外押金。申请说明和分成比例属于链群行动执行合约数据，比例统一使用 `1e18` 精度。
- **申请与冻结**：投票阶段内可新增、撤销或修改申请；撤销/修改立即清空该成员本轮候选投票。投票阶段结束后，本轮候选、排名和分成比例冻结，之后的变更只影响下一轮。
- **验证开放时间**：初始化传入严格递增的验证阶段分割线数组；第 1 名在验证阶段开始时可提交，数组有 `n` 个分割线时排名前 `n + 1` 名可提交。分割线满足 `0 < split < 1e18`，开放区块按验证阶段起始区块及阶段区块数计算；数组为空时仅第 1 名可提交。
- **验证集合与批次**：行动阶段结束时快照所有至少有一个参与成员的链群 NFT，空链群不纳入；后续链群停用、恢复或新增不改变本轮集合。每个链群按快照成员历史顺序维护连续游标，`startIndex` 必须等于已验证数量，支持分批提交，禁止重复、跳过或乱序。
- **本轮锁定与授权**：首个有效批次永久锁定本轮公共验证者 `memberId`，不设置失效、接管或代理；之后批次只能由该 `memberId` 当前 `MemberNFT` 持有人提交。NFT 转移后由新持有人继续，锁定的身份不变。
- **完成条件与激励**：公共验证者必须完成全部快照链群的验证才算成功。验证不完整时，链群行动、行动者、链群服务、公共验证者和链群 owner 的相关激励全部为 `0`；独立的底层治理激励不受影响。完整时，公共验证者从链群服务激励总额中按冻结比例 `r` 获得 `总额 × r`，余下按链群服务规则分配给链群 owner。
- **链群 owner 与监督**：链群 owner 是链群 NFT（`groupId`）主体，不是钱包地址；不再保留群级验证 delegate 或代理验证者。治理者在投票阶段同时为行动和候选人投票，下一轮不给有问题的候选人投票完成监督，不回溯扣减历史奖励。
- **底层回调边界**：`Vote` 只传递 `proposalId` 与逐提案不透明 KV；没有 KV 时不回调，回调失败回滚整笔投票交易。候选竞选、快照、批量验证和服务激励均由链群行动/服务行动执行合约处理，底层治理合约不解析这些业务字段。
