# 三层合约架构与职责边界

Type: grilling
Status: resolved
Blocked by:

## Question

明确 BSC 版协议中底层治理框架、通用行动框架和具体行动执行合约之间的职责边界，避免把链群公共验证者等特定行动逻辑放入通用层或核心治理合约。

## Comments

用户确认：当前协议至少分为三层。最底层是由 `Stake`、`Submit`、`Vote` 和 `Mint` 组成的治理框架；其上是通用行动框架；最上层是各种具体的行动执行合约。

## Answer

BSC 版协议采用三层业务架构：

1. **底层治理框架**：由 `Stake`、`Submit`、`Vote` 和 `Mint` 组成。它负责治理资产、提案基础数据、治理投票和奖励铸造等通用能力；治理激励只按底层治理规则结算，不读取具体行动执行合约的验证结果。
2. **业务扩展框架层**：当前由通用行动框架合约 `LOVE20Action` 实现，包含行动数据、提案到行动的映射初始化、参与登记和应急清理入口；未来可增加与行动框架并列的其他扩展框架。行动框架不托管资产，也不定义公共验证者、链群、验证快照或行动奖励二次分配等业务。
3. **具体扩展执行层**：当前由不同类型的行动执行合约实现。执行合约自行定义参与、资产托管、验证、激励二次分配和治理投票 KV 的业务含义。链群行动的公共验证者竞选、验证集合、链群 owner 以及链群服务行动的分配，均属于链群行动执行层。

`LOVE20Phase` 是跨层共享的无语义时间线基础设施，不属于上述三层中的业务层；各层按自身语义使用它。`executor` 可以是具体执行合约，也可以是 EOA；当没有执行合约逻辑时，不应为了分层而新增空壳合约。

参与资产、扩展资产及其返还和行动内分配均由具体行动执行合约自行托管和处理，`LOVE20Action` 不接收或持有行动资产。

正常加入、退出和资产取回均通过具体行动执行合约完成。`forceExit` 只是执行合约失效时绕过它、清理通用参与登记的最后兜底，可能导致资产无法返还；前端首版不提供该入口。

跨层调用只依赖稳定的通用边界：`Vote` 仅透传提案定位信息和不透明 KV，`Mint` 提供按提案或行动授权的一次性激励铸造，具体业务字段和规则由扩展层自行解析和执行。
