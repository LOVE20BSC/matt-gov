# 两层主架构与提案 Target 边界

Type: grilling
Status: resolved
Blocked by:

## Question

明确 BSC 版协议中核心治理层与提案扩展层的职责边界，避免把链群公共验证者等特定行动逻辑放入核心或所有提案类型共享的 Target 边界。

## Comments

用户确认：当前协议至少分为三层。最底层是由 `Stake`、`Submit`、`Vote` 和 `Mint` 组成的治理框架；其上是通用行动框架；最上层是各种具体的行动执行合约。

用户修订：从协议主架构看统一为两层：底层核心治理层，以及按提案类型划分的提案扩展层。当前只有社群行动类型；该类型内部的 `ActionTarget` 是否再拆分执行器、验证器或分配器，属于自身业务结构，不再定义为协议级第三层。

## Answer

BSC 版协议采用两层主架构：

1. **核心治理层**：由 `Stake`、`Submit`、`Vote` 和 `Mint` 组成，并包含 `MemberNFT`、`LOVE20Phase` 以及基础子币发射能力（发射次数账本、次数融合/消耗和子币创建）。它负责治理资产、提案基础数据、治理投票、激励铸造和基础发射流程等通用能力；治理激励只按核心治理规则结算，不读取提案扩展的业务结果。
2. **提案扩展层**：按提案类型实现 `Target` 合约。当前社群行动类型使用 `ActionTarget`，负责该类型提案的创建回调、映射和通用参与登记，并承载 LP、链群行动及链群服务行动执行合约。`ActionTarget` 内部可以按业务需要拆分执行器、验证器或分配器，但这些不是协议级架构层。

`LOVE20Phase` 是跨层共享的无语义时间线基础设施，不属于上述两层中的业务层；各层按自身语义使用它。

参与资产、扩展资产及其返还和行动内分配均由提案类型内部业务自行托管和处理，`ActionTarget` 不接收或持有行动资产。

正常加入、退出和资产取回均通过提案类型内部业务完成。`forceExit` 只是内部业务失效时绕过它、清理通用参与登记的最后兜底，可能导致资产无法返还；前端首版不提供该入口。

跨层调用只依赖稳定的通用边界：`Vote` 透传提案定位信息、本次投票对应的 `memberId`、治理票增量和不透明 KV，但不解析扩展业务；`Mint` 提供按提案授权的一次性激励铸造，其他具体业务字段和规则由对应 `Target` 自行解析和执行。
