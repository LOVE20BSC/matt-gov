# 三层合约架构与职责边界

Type: grilling
Status: resolved
Blocked by:

## Question

明确 BSC 版协议中底层治理框架、通用行动框架和具体行动执行合约之间的职责边界，避免把链群公共验证者等特定行动逻辑放入通用层或核心治理合约。

## Comments

用户确认：当前协议至少分为三层。最底层是由 `Stake`、`Submit`、`Vote` 和 `Mint` 组成的治理框架；其上是通用行动框架；最上层是各种具体的行动执行合约。

## Answer

BSC 版协议采用三层业务架构：

1. **底层治理框架**：由 `Stake`、`Submit`、`Vote` 和 `Mint` 组成。它负责治理资产、提案/行动基础数据、治理投票和奖励铸造等通用能力；治理激励只按底层治理规则结算，不读取具体行动执行合约的验证结果。
2. **通用行动框架**：由 `LOVE20Join` 及通用行动数据、参与登记和强制退出入口组成。它只处理所有行动都需要的生命周期能力，不托管资产，也不定义公共验证者、链群、验证快照或行动奖励二次分配等业务。
3. **具体行动执行层**：由不同类型的行动执行合约实现。执行合约自行定义行动参与、验证、行动激励领取后的二次分配和治理投票 KV 的业务含义。链群行动的公共验证者竞选、验证集合、链群 owner 以及链群服务行动的分配，均属于这一层。

`LOVE20Phase` 是跨层共享的无语义时间线基础设施，不属于上述三层中的业务层；各层按自身语义使用它。`executor` 可以是具体执行合约，也可以是 EOA；当没有执行合约逻辑时，不应为了分层而新增空壳合约。

参与资产、扩展资产及其返还和行动内分配均由具体行动执行合约自行托管和处理，`LOVE20Join` 不接收或持有行动资产。

跨层调用只依赖稳定的通用边界：`Vote` 仅透传行动定位信息和不透明 KV，`Mint` 提供按行动授权的一次性激励铸造，具体业务字段和规则由第三层自行解析和执行。
