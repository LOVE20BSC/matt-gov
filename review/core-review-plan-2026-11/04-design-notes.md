# 04 · 设计层命题 D-01..D-10

每个子系统问一次，不依赖文档。判定只有三档：**兑现** / **可接受（约束条件 + 失效边界 + 损失承担者）** / **缺陷**。三件套缺一即判缺陷。

汇总：兑现 2（D-04、D-09）｜可接受 7（D-01、D-02、D-03、D-05、D-07、D-08、D-10）｜缺陷 1（D-06）。

## D-01 · 票权杠杆无上限 → **可接受（附约束）**

| 项 | 内容 |
| --- | --- |
| 命题 | `govVotes = liquidityShares × promisedWaitingPhases`，`stakeBoost` 只要 1 wei 就能把乘数从 MIN 拉到 MAX |
| 机制 | `Stake:875`、`Stake:154-159`、`Stake:467-473` |
| 若成立意味着 | 1 wei 换 MAX× 票权，治理可被低成本收购 |

### 判定

**乘数本身可接受，但它与提交门槛的组合是缺陷（STK-01）。** 两件事必须分开：

- 投票权 ∝ 资本 × 时间，是 veToken 的经典取舍。要拿 MAX 倍票权，必须承诺 MAX 期锁仓；`withdraw:235` 的真实等待让这个承诺有成本。「1 wei」不是对价，只是触发条件——对价是锁定期。
- 提交门槛 `required = ratio × totalValidGovVotes` 用的是**活的**分母，于是同一个乘数可以从「提升自己」变成「排除别人」。这一面没有对价：`ratio < 1` 时攻击者只要抬得比谁都高就永久独占提案权，而他并不需要真的比别人锁得久——只需要在别人不抬的时候抬一次。

| 三件套 | 内容 |
| --- | --- |
| 约束条件 | ①`MIN > 0`（`DeployCore:168` 保证）；②`MAX` 必须对应一个有意义的时间跨度（若 `MAX = 3`，杠杆只有 3 倍）；③`MAX = MIN` 时杠杆消失 |
| 失效边界 | `MAX/MIN` 越大，单位票权的资本成本越低；`phases` 只增不减（`Stake:123-125`、`143-145`），一旦拉满不可回退，所以「拉满」是一次性、不可撤销的身份变更 |
| 损失承担者 | 选择短锁定期的小份额持有人：他们的相对票权被稀释，且（经 STK-01）失去提交权。资产不受损 |

### 上限在哪

不在乘数，在**总票权的构成**：`Σ shares × phases`。票权总量随所有人锁定期变长而膨胀，所以「占总票权比例」这个量对个体是零和的，对系统是通胀的。真正需要设上限的是「门槛的分母是否可以被单方面移动」——见 STK-01。

## D-02 · 手续费归属 = 任何 LP 增值 → **可接受（附约束）**

| 项 | 内容 |
| --- | --- |
| 命题 | `_reclassify` 用 `sqrt(k)` 增量判手续费，`_reserves` 只读 `getReserves()` 不读余额 |
| 机制 | `Stake:684-691`、`Stake:655-669`、`Stake:782-784` |
| 若成立意味着 | 捐赠、他人交易费、价格操纵造成的 k 变化全被判成协议收入，改标量被烧掉；重分类无单次上限、逐轮可重复 |

### 判定

命题成立，但**结论与计划的预期相反**：这不构成对持有人的损害。

用 `V(w) = w·sqrt(k)/TS` 度量 LP 的几何价值，重分类后的可提取部分满足

```
V(W') = W·(b0/b1)·sqrt(k1)/TS = W·sqrt(k0)/TS = V(W)
```

即**本金在几何价值上严格守恒**，全部 k 增长被记进 `F`（待销毁）。所以：

- 捐赠者不能把别人的钱变成自己的——他自己的捐赠大部分进了待销毁账户；
- 被捐赠的社区持有人不吃亏；
- 「重分类无单次上限、逐轮可重复」是对的，但重复只是把更多 W 划到 F，而 F 的出口只有 `_realizeFees` 的 0.25%/phase 节流。

| 三件套 | 内容 |
| --- | --- |
| 约束条件 | 池子必须是标准 V2（`getReserves` 与余额同源、`sync` 可用、`burn` 按比例付款）。换成一个可以任意改写 `getReserves` 的池子，守恒证明立刻失效 |
| 失效边界 | 捐赠未 `sync` 时不可见（`_reserves` 读存储值），要等下一次 `mint`/`burn`/`swap` 才被计入。因此「捐赠 → 立即提取」不改变任何数字 |
| 损失承担者 | 捐赠者自己。任何想通过「捐赠 + sync」操纵分配的第三方，净效果是自损 |

### 一个真实的副作用

`_settleFees` 每次都会改写 `lastFeeLp/lastWithdrawableLp/lastSqrtKOfLp`，但只有真正销毁时才发 `FeesSettled`。**只重分类不销毁**的那一次没有任何事件 → 链下无法重建 W/F 拆分。这不是分配问题，是可观测性问题，记入 D-06。

## D-03 · 结算吞吐有硬上限 → **可接受（附约束）**

| 项 | 内容 |
| --- | --- |
| 命题 | 每社区每 Phase 一次 + 单笔 0.25%，单价按 `withdrawableLp` 计价 |
| 机制 | `Stake:786-796`、`Stake:818`、`Stake:835` |
| 若成立意味着 | 若 `feeLp` 增速 > 0.25%/Phase，积压单调增长；`lastWithdrawableLp` 被压到 0 后 `settlementUnit == 0`，`_canBurn` 恒假 → 出口取决于他人新质押 |

### 判定

成立，但两个不等式都远未到临界：

1. **增速**：单 phase 能处理 `0.25% × W` 的 LP。要让积压增长，池子每 phase 要产生相当于 `W` 的 0.25% 的手续费。以 0.3% 费率计，需要每 phase 成交额与 `W` 同量级（手续费按 sqrt(k) 度量只取其中约一半，所以量级还要再高一点）。单个社区的池子做不到持续这个量级。
2. **停摆**：`W → 0` 只有在所有持有人都提取完毕时发生，此时「结算停摆」的受害者是协议的待销毁手续费，不是用户。有新质押即恢复（`STK-05`）。

| 三件套 | 内容 |
| --- | --- |
| 约束条件 | `FEE_SETTLEMENT_RATIO ≤ 池费率`（部署层强制 2.5e15 ≤ 0.3%），否则单次结算的价格冲击超过一次往返成本，`P-02` 的套利不等式翻转 |
| 失效边界 | 每 phase 一次的节流由 `_lastSettlePhase` 硬编码（`Stake:791`），无法提高；`W` 越小单次处理量越小，形成「越穷越难结算」的正反馈 |
| 损失承担者 | 协议自身（未销毁的手续费滞留）。用户资产不受影响 |

## D-04 · 协议存在直接 LP 出口 → **兑现**

| 项 | 内容 |
| --- | --- |
| 命题 | `_canBurn` 失败时 LP 直接给提取者 |
| 机制 | `Stake:748-758`、`Stake:804-810` |
| 若成立意味着 | 同一份额对不同人价值不同；拿到 LP 可立即自行 burn，等价于「拿不到双币但能提前退出」 |

### 判定

**兑现，且是精确的兜底，不是绕过。**

`_canBurn(lp) ≡ lp·r_t ≥ TS ∧ lp·r_p ≥ TS` 与真实 `pair.burn` 的 `require(amount0 > 0 && amount1 > 0, "INSUFFICIENT_LIQUIDITY_BURNED")` 在整数上严格等价：

```
floor(lp·r/TS) ≥ 1  ⇔  lp·r ≥ TS
```

所以这条分支的触发条件恰好是「burn 会 revert」，而不是「burn 不划算」。测试 `test_zeroValueBurnFallsBackToLpTransfer` 构造了 `lp = 3`、`TS = 3,159,003`、`r_t = 1e6` 的真实边界，断言 `_canBurn == false` 且持有人拿到 3 LP 而不是 revert。

关于「提前退出」：`withdraw` 的前置等待期（`Stake:235`）已经满足，LP 出口不提前任何时点；LP 与双币等值（同一份额在池中的索取权）。所以它既不加速退出，也不改变价值，只是把「不可能成功的 burn」换成「直接交付凭证」。

### 附带的真问题

`lpAmount == 0` 与 `_canBurn == false` 共用同一条静默路径，前者什么都不给（`STK-02`）。这是兜底逻辑的边界泄漏，记在 STK-02。

## D-05 · 发射次数双账本 → **可接受（附约束）**

| 项 | 内容 |
| --- | --- |
| 命题 | `addLaunchCount` 同时给 FIRST 与 ROOT 记账，但 `MAX_LAUNCH_COUNT` 只校验 FIRST |
| 机制 | `Launch:187-204`、`Launch:334-349` |
| 若成立意味着 | ROOT 的剩余次数可无限增长？根级与社区级是否应共享上限？两个账本哪个是权威？ |

### 判定

三个问题逐一回答：

1. **ROOT 的剩余会无限增长吗**：会，但只随 FIRST 的 issued 增长而增长，而 FIRST 的 issued 被 `MAX_LAUNCH_COUNT` 卡住（`:194-197`）。所以 ROOT 的剩余上界 = `MAX_LAUNCH_COUNT × 成员数`，不是无限。
2. **根级与社区级应否共享上限**：现状是「同一份额度支持两次发射（根级一次、首币级一次）」，因为两者挂在不同的父节点下，是不同的权利，不是重复消费。若共享，等于把「根级发射」变成「首币发射」的子集，与「一个社区可以同时有根级子社区与首币子社区」的模型冲突。
3. **哪个账本是权威**：`_issuedLaunchCount` 是权威（只增、用于限流、`Launch:51` 的注释写明「消费与合并都不减少」）；`_remainingLaunchCount` 是可转移的**消费权**（`mergeLaunchCount` 可搬）。两者不构成「双账本对账」关系，而是「配额」与「已发」两个不同维度。

| 三件套 | 内容 |
| --- | --- |
| 约束条件 | `ROOT` 必须是不可铸造的父币（`DeployCore:85` 取 `router.WETH()`）。若 ROOT 本身也是一个可被 `Mint` 记账的社区代币，`_issuedLaunchCount[ROOT]` 会被两条路径同时写，`MAX_LAUNCH_COUNT` 的比较就失效 |
| 失效边界 | 社区总数上限 = `2 × MAX_LAUNCH_COUNT`（首币级 + 根级）；`_issuedLaunchCount[ROOT]` 可超过 `MAX_LAUNCH_COUNT`，但没有任何读取方把它当上限用 |
| 损失承担者 | 无 |

## D-06 · 「销毁」名不副实 → **缺陷（Low）**

| 项 | 内容 |
| --- | --- |
| 命题 | `_burnCancelledPool` 只加 `_rewardBurned`，代币从未存在；`_settleFees` 改写总量却不发事件 |
| 机制 | `Mint:163-173`、`Mint:526-543`、`Stake:782-784` |
| 若成立意味着 | 事件 `RewardBurned` 会被索引器读成「销毁了代币」；改标时序在事件流里完全不可重建 |

### 判定

成立，判缺陷。两处独立：

1. **`Mint`**：`_rewardBurned` 增、`totalSupply` 不变、同一笔额度经 `reservedAvailable` 回流 `rewardAvailable`（`Mint:459`）下一轮可再预留。事件名与语义不符：它不是 burn，是「配额作废」。同一事件在 `Mint:537` 的 `BoostOverflow` 又是另一层意思（从待铸额度里划掉、永不铸造）。两个 reason 共享一个事件名，只能靠字段区分。
2. **`Stake`**：`_settleFees` 每次改写三个存储量，但只在 `_realizeFees` 里发 `FeesSettled`。只重分类的调用没有任何日志 → 链下无法从事件重建 W/F 的拆分，只能靠轮询 `totalStake` 快照。

为什么只判 Low：不影响任何人的余额，只影响「用日志重建状态」的能力。但如果协议把「销毁量」当作对外披露指标（`totalBurnedToken`/`rewardBurned`），口径必须写清楚是「配额作废」还是「供应减少」。

| 三件套 | 内容 |
| --- | --- |
| 约束条件 | 无（现状无法让事件语义自洽） |
| 失效边界 | 任何以 `RewardBurned` 为输入的供应量推导都会错，误差 = Σ 被取消额度 |
| 损失承担者 | 数据消费者（索引器、看板、审计） |

## D-07 · 身份定价反向 → **可接受（附约束）**

| 项 | 内容 |
| --- | --- |
| 命题 | `calculateMintCost`：成本 ∝ 未铸供应，越接近上限越便宜 |
| 机制 | `MemberNFT:108-121` |
| 若成立意味着 | 早期参与者最贵、晚期免费。是「抑制早期囤积」还是「必然通胀到免费」？ |

### 判定

**必然到免费**，免费区宽度恰好是 `BASE_DIVISOR`（`unminted / BASE_DIVISOR == 0` 的区间）。这不是「抑制囤积」——它对早期更贵、晚期更便宜，与囤积的方向相反（想囤的人会等）。

能接受的理由是身份不携带链上权利：

- 票权来自 `Stake`（`validGovVotes`），与 memberId 数量无关；
- 发射额度来自 `Launch._remainingLaunchCount`，需要靠铸币奖励挣；
- 提交提案需要票权门槛，免费身份不带来票权；
- 身份费是烧掉的（`MemberNFT:86`），免费铸造不产生通胀。

| 三件套 | 内容 |
| --- | --- |
| 约束条件 | 任何「按 memberId 计数」的配额都必须另设门槛（例如每成员每轮一次 + 票权门槛），否则免费身份可以绕过 |
| 失效边界 | 免费区 = 最后 `BASE_DIVISOR` wei 的供应；`BASE_DIVISOR` 越大，免费区越宽 |
| 损失承担者 | 无资产损失；代价是 memberId 空间被廉价占用（`_nextTokenId` 单调，无回收） |

## D-08 · 时间轴可被放大 → **可接受（附约束）**

| 项 | 内容 |
| --- | --- |
| 命题 | `sync` 只保 `newPhaseBlocks ≥ 1`，观测窗由首个调用者选 |
| 机制 | `Phase:86-136`、`Phase:116-121`、`Submit:319-322` |
| 若成立意味着 | 轮长被放大 100× 后，Stake 等待期、Mint 的「轮已结束」、Vote 的轮次推进同时变形。首推者与出块者的影响力边界在哪？ |

### 判定

**机制上没有上界，实际上需要时间戳异常。** 边界划分清楚：

| 角色 | 能影响什么 | 不能影响什么 |
| --- | --- | --- |
| 首个调用者（通常是当轮首个提交者） | 观测**时刻**（决定窗口起点） | 窗口内的块数/秒数比例 |
| 出块者 | 时间戳（决定 `elapsedSeconds`） | 观测时刻的选择（除非也抢首推） |
| 普通用户 | 无 | 无 |

所以「放大 100 倍」需要 `elapsedSeconds ≪ elapsedBlocks × 正常出块间隔`。同一块内所有交易共享时间戳，普通交易排序造不出这个比例。

**保护性设计是充分的**：`_recordNextSegment` 把新段起点算在 `phase+1` 边界（`:155-159`），`phaseAtBlock` 用 `nearest(startBlock)` 查找，所以 `currentPhase` 在同一笔交易内不跳变——`Submit` 的「首推触发 sync」不会让自己那一笔跨轮。测试 `test_phaseBlocksHasNoUpperClamp` 同时验证了这两点：`phaseInfo(4) = 1,001,000` 而 `phaseInfo(3) = 1000`。

| 三件套 | 内容 |
| --- | --- |
| 约束条件 | `TARGET_SECONDS` 必须与真实出块间隔同量级（否则日常就会连续触发大幅调整）；`ADJUST_THRESHOLD > 0`（`DeployCore:137-140`） |
| 失效边界 | 单次异常窗口可把 `phaseBlocks` 写成任意值，且新段没有回退路径——只能靠下一次偏差再调回来，而「调回来」同样要越过阈值 |
| 损失承担者 | 所有依赖 phase 的时序：`Stake` 的解锁等待、`Mint` 的「轮已结束」、`Vote`/`Submit` 的轮次推进。没有任何一方能单方面修复 |

## D-09 · 回调身份靠目标自证 → **兑现**

| 项 | 内容 |
| --- | --- |
| 命题 | core 不传 `msg.sender` 给 `onProposal*`/`onTokenLaunched`；`Mint:179-183` 反向用 `Submit.proposalTarget` 校验调用者 |
| 机制 | `Submit:326-338`、`Vote:281-287`、`Launch:149-151`、`Mint:175-184` |
| 若成立意味着 | 恶意 target 可让别人的提交/投票整笔失败；高 gas 目标可让票权记录不可用；回调内是否可达「半写」状态 |

### 判定

逐条兑现：

1. **恶意 target 能否让别人的整笔失败**：不能。`target` 由提案作者在 `ProposalBody` 里指定（`Submit:235`），只有作者自己的提交/投票会进这个 target。别人的交易不会碰它（`Vote` 只有投票给该提案的人才进）。
2. **高 gas 目标能否让票权记录不可用**：只对该提案有效。投票人投这一票会全额 revert（含状态），可以分批绕开（`Vote:93-99` 逐提案循环，但整批原子）。受害面限于「该提案自己」。
3. **回调内是否可达半写状态**：不可达。三个面的写入顺序都是「先写状态、再回调」：
   - `Submit:301-307` 三张表 → `:326` `onProposalCreated`；
   - `Vote:256-259` 四个累计量 → `:286` `onProposalVoted`；
   - `Launch:133-147` 登记齐全 → `:150` `onTokenLaunched`。

   所以回调里的任何重入看到的是**已完成**的状态。`Stake._hasUsedStakeRights` 依赖这一点（读 `Submit.proposalIdBySubmitterId`），测试 `test_mergeInsideProposalCreatedIsBlockedByWrittenState` 用完整 revert data 断言了它。
4. **`Mint` 的反向校验**：`onlyProposalTarget`（`Mint:175-184`）用 `Submit.proposalTarget` 反查，不依赖 target 自报身份。这意味着 target 无法替别人的提案领奖——它只能领自己那条。

结论：回调面是安全的，安全性来自「作者自选 target + 先写后调」两条，缺一不可。

## D-10 · 参数域完全在链外 → **可接受（附约束）**

| 项 | 内容 |
| --- | --- |
| 命题 | 7 个 `init` 只防重复 |
| 机制 | `Stake:83-94`、`Mint:82-98`、`Submit:55-58`、`Vote:52-55`、`Launch:55-66`、`MemberNFT:55-58`（`Phase` 走构造函数） |
| 若成立意味着 | 一旦部署脚本被绕过，哪些参数让协议永久不可用且无自愈？是否值得一条链上 `require`？ |

### 判定

把「永久不可用」的参数组合穷举一遍，逐个查三层（链上 / 广播前 / 广播后）：

| 组合 | 后果 | 链上 | 广播前 | 广播后 | 判定 |
| --- | --- | --- | --- | --- | --- |

所以命题成立，但结论是「四层防线已闭合到只剩两个洞」，而不是「完全在链外」：

- 大部分参数有**两层**（广播前 + 广播后），并且 `21_check` 的关键几项是**从链上读回值再比较**（`:250-265`），不是复制字面量；
- 真正没有防线的是 MemberNFT 的指数上界（`NFT-03`）与 `init` 的时序（`DEP-01`）。

| 三件套 | 内容 |
| --- | --- |
| 约束条件 | 部署必须走 `11_deploy.sh` 全流程（含 `21_check.sh` 的非零退出检查）；`--slow` 是让抢跑窗口存在的直接原因 |
| 失效边界 | 只有 `MemberNFT` 的指数组合与 `init` 时序没有防线；其余参数的最坏后果在广播前就被拒 |
| 损失承担者 | 部署方（重部署成本）；条件性地，若无视非零退出继续公布地址，则用户承担 |

### 是否值得一条链上 `require`

只对两处有意义：

1. `MemberNFT` 构造函数里的指数上界（一次性、纯算术、零运行期成本）；
2. `init` 的调用者限制（例如只允许 `tx.origin == 部署者` 或一个 `deployer` 常量）——但这一步会引入新的信任假设。

其余参数加链上 `require` 的收益很低：它们都是「一次性常量」，链上校验只是把广播前的检查复制一遍，反而增加部署时的 gas 与失败点。
