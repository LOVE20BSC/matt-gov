# P-04 · 已解锁未提取窗口

**路径**：`unstake:183` → `withdraw:223` → `_withdrawLiquidity:737` → `_settleFees:775` → `_push:508`

**固定三问**：状态修改顺序有无可利用窗口 / 攻击者能在哪个时点插入什么 / 结论落在哪个不变量。

## 两个函数各自改了什么

```
unstake(token, memberId)                        withdraw(token, memberId)
─────────────────────────────────────────────   ────────────────────────────────────────

Stake:188  _checkStakedLiquidity                Stake:229  _checkStakedLiquidity
Stake:191  !_hasUsedStakeRights(round)          Stake:235  round > unlock + phases
Stake:198  member.unlockRequestPhase = round    Stake:239  _withdrawLiquidity(...)

                                                │  :750-757  burn 或把 LP 转给成员

```

**这就是窗口的形态**：`unstake` 之后，`member.boostShares` 仍在合约里、`totalBoostShares` 仍包含它，但 `validBoostShares` 已经归零（`Vote`/`Mint` 不再计它）。

## 谁能动这笔钱

| 角色 | 能做什么 | 依据 |
| --- | --- | --- |
| 持有人自己 | `withdraw`（等过等待期后） | `Stake:235` |
| 同一社区的其他人 | 不能：`withdraw` 有 `onlyMemberOwner`，`_memberStake` 按 `[token][memberId]` 隔离 | `Stake:223`、`:227` |
| 结算链 | 只能烧 `feeLp`，不能烧 `boostShares` | `_realizeFees:835` 只减 `lastFeeLp`；`burn:831` 烧的量恒等于本轮刚收到的量 |
| `mergeStake` | 不能：`_checkNoUnstakeRequest(target)` 挡住「已申请解锁」的 target | `Stake:282` |

## 攻击者能插入什么

| 时点 | 动作 | 结果 |
| --- | --- | --- |
| `unstake` 之后、`withdraw` 之前 | `stakeBoost` / `stakeLiquidity` / `mergeStake` 到自己 | **revert `UnstakeAlreadyRequested`**（`Stake:122`、`:141`、`:281`） |
| 同上 | 别人往池子里加流动性 | 该持有人的份额被稀释但 W 同比例增长，索取权不变（`S6` 恒等式） |
| 同上 | 任何人 `settleFees` | 重分类把 W 压小、F 变大；持有人的**几何价值不变**（`STK-04` 守恒证明） |
| `withdraw` 执行中 | 重入 `withdraw` | 不可达：三条转账无钩子（`STK-03`）；若可达，`pair.burn` 的 `lock` 会挡住嵌套 burn |
| `withdraw` 之后 | 「再质押 → 再解锁」 | 可以，但 `delete` 已清空记录、boost 已退给本人，**必须重新转入资产**——不能复用同一份 |

## 结论落在哪个不变量

> **`balanceOf(stake, token) ≥ Σ member.boostShares + 在途结算的临时余额`**

三条支撑：

1. **入**：`stakeBoost:148` 按 `boostAmount` 拉入，同时 `member.boostShares += boostAmount`、`totalBoostShares += boostAmount`，三者同步。
2. **出**：只有一个出口 `withdraw:244-247`，扣的量恒为 `member.boostShares`，并同步扣 `totalBoostShares`。
3. **绕过**：`_realizeFees` 的 `burn(831)` 只烧它刚收到的量——`_burnLp:821` 把两种币付给 `address(this)`，`_swapParentTokenForToken:827` 把父币换成社区币也付给 `address(this)`，随后烧掉它们的和。净流入 0，不触碰押金。

测试 `test_settlementNeverTouchesBoostBacking`：两人各押 4e17 / 6e17（合计 1e18），向 pair 捐赠 3e20 + `sync`，触发结算后断言 `totalBoostShares == 1e18` 且 `balanceOf(stake) ≥ 1e18`。

## 判定

| 项 | 结论 |
| --- | --- |
| 「已解锁未提取」期间谁能动这笔钱 | **只有持有人自己**（等过等待期）；结算链只碰 `feeLp` |
| `:821/:831` 的 burn 会不会吃到该负债 | **不会**，净流入为零（已测） |
| 「提取 → 再质押 → 再解锁」能否复用同一份资产 | **不能**。`delete` 清空记录，boost 已转出；再质押需要新转入 |
| 窗口内的票权 | 已归零（`unstake:199-205`），所以不能「锁着票权慢慢退出」 |
| 窗口内的风险 | 只有 `STK-02`（份额价值不足 1 LP 时静默丢失）与 `STK-05`（`W → 0` 结算停摆） |

**一句话**：这个窗口是**故意的**——解锁先撤票权、后撤资产，中间留出等待期。资产侧由「入出同步 + 净流入为零」两条守住，没有第三方可取。
