# P-06 · 四个账本的守恒

**路径**：`_prepareRewardIfNeeded:126` → `_mintGovReward:500` → `_updateLaunchCredit:463` → `Launch.addLaunchCount:187` → `_addLaunchCount:334` → `LOVE20Token.mint:42`

**固定三问**：状态修改顺序有无可利用窗口 / 攻击者能在哪个时点插入什么 / 结论落在哪个不变量。

## 四个账本

| 账本 | 定义 | 写入点 | 单调性 |
| --- | --- | --- | --- |
| **奖励额度** | `_rewardReserved` / `_rewardMinted` / `_rewardBurned` | `Mint:130`（只 reserved）、`:208`、`:526`、`:528` | 三者都只增 |
| **发射累计** | `_issuedLaunchCount[token]` | `Launch:339-340` | 只增（`Launch:51` 注释明示「消费与合并都不减少」） |
| **发射余额** | `_remainingLaunchCount[token][member]` | `Launch:341`、`:174-175`、`:111` | 增减皆有 |
| **发射信用** | `_launchCredit[token][member]` | `Mint:485`、`:495` | 增减皆有 |

## 恒等式

### ① `reservedAvailable ≥ 0`

```
reservedAvailable = R − M − B
available        = (MAX − TS) − reservedAvailable
```

预留时 `R += gov + prop`，其中 `gov + prop ≤ available`（`Mint:127-130`，比例之和 ≤ 1e18 由部署层强制）；铸造/销毁时 `M + B` 的增量逐成员 ≤ 该成员应得额度，Σ ≤ `gov + prop`。所以 `R − M − B` 只会被「未认领的部分」抬高，永不为负。**这条是 `rewardAvailable:455` 不下溢的唯一依据。**

### ② 每轮 `Σ(mint + burn) ≤ R_round`

治理侧：`voteReward ≤ votePool`（`Mint:391`，分母是全轮投票总额）、`boostReward ≤ boostPool`（`:403-406`）、`burnReward = theoretical − boostReward`（`:407`），逐成员三项和 ≤ `govReward`。

提案侧：`Σ amount(p) = proposalReward × Σ voteAmount(p) / eligibleVoteAmount = proposalReward`（逐项 floor 只会更小），求和域与分母同源，证明见 `03-findings/mint.md` 的「M4 不成立」。

### ③ `_issued = consumed + Σ remaining`

`addLaunchCount` 同时 `_issued += count` 与 `remaining[member] += count`；`mergeLaunchCount` 只在成员之间搬；`launchToken` 只减 `remaining`、不动 `_issued`。所以对任一 `token`：

```
_issuedLaunchCount[token] = (# launchToken 调用数) + Σ_members remaining[token][member]
```

### ④ 根级镜像

`Launch:201-203`：`token == FIRST` 时同一笔 `count` 也记到 `ROOT` 名下。所以

```
_issued[ROOT] = Σ_{FIRST 的每一次记账} count
Σ remaining[ROOT] = _issued[ROOT] − consumed_root
```

`_issued[ROOT]` 因此可以超过 `MAX_LAUNCH_COUNT`——但没有任何读取方把它当上限（`Mint:469-470` 只读被奖励代币自己的 `issuedLaunchCount`）。

## 攻击者能插入什么

| 时点 | 动作 | 影响 |
| --- | --- | --- |
| 轮 N 结束后、轮 N+1 结束前 | 先 mint N+1 | 抢走配额（`MNT-01`），但恒等式 ① 仍成立 |
| mint 过程中 | 无重入点：`token.mint` 与 `addLaunchCount` 都是本仓合约，无钩子 | — |
| `addLaunchCount` 时 | 无法直接调用（`onlyMint`） | — |
| `launchToken` 时 | 先减 `remaining` 再建币，失败整笔回滚（`Launch:110-119`） | 不会出现「扣了额度没建币」 |

## 事件折叠 == view 的对账表

| 量 | 事件来源 | 能否从日志重建 |
| --- | --- | --- |
| `_rewardReserved` | `RewardPrepared.rewardReserved`（累计值） | 是 |
| `_rewardBurned` | `RewardPrepared.rewardBurned`（累计）+ `GovRewardMinted.burnReward` + `RewardBurned`（`BoostOverflow`） | 是（注意 `_burnCancelledPool` 的额度也记在 `RewardPrepared` 的累计值里） |
| `_rewardMinted` | `GovRewardMinted(voteReward + boostReward)` + `ProposalRewardMinted.amount` | 是 |
| `_issuedLaunchCount` | `LaunchCountAdded.issuedCount`（累计） | 是 |
| `_remainingLaunchCount` | `LaunchCountAdded.memberRemaining`、`LaunchCountConsumed.remaining`、`LaunchCountMerged.source/targetRemaining` | 是 |
| `_launchCredit` | **没有事件** | **否**（只有 `launchCredit()` view） |
| `totalSupply` | `TokenMinted` / `TokenBurned` + 构造函数的初始铸造 | 是 |

唯一的缺口是 `_launchCredit`：它是「已铸但还没攒够一个阈值」的残余，转换时才发 `LaunchCountAdded`。所以链下要么轮询 view，要么用「铸币量 − 已转换量」自己算，但后者需要知道每次转换时的 `threshold`（随时间下降）。

## 结论落在哪个不变量

> **`MAX_SUPPLY` 是所有账本的共同上界**：`TS + reservedAvailable ≤ MAX_SUPPLY`，且 `issued`/`remaining` 与供应无关（只影响发射权，不影响币量）。

前者由 ① 保证；后者由 `Launch` 独立记账保证。两套账本唯一的交集是「铸币量 → 发射信用」，而那一步只读 `mintedAmount` 与当时的供应，不回写供应。

## 判定

| 项 | 结论 |
| --- | --- |
| 四账本守恒 | **成立**，①②③④ 全部可证；无越预留、无负余额 |
| `threshold` 用 mint 前供应、`launchCredit` 跨轮累加 | **不吞额度**。credit 是「代币记账的余额」，按当前 `threshold` 兑换；`threshold` 随时间下降 → 晚兑换反而更划算，方向与「吞」相反 |
| 事件折叠 == view | **除 `_launchCredit` 外全部可重建** |
| 抢跑 mint 顺序 | **可改变分配**（`MNT-01`），但不破坏任何恒等式 |
