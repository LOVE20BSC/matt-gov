## 三个需要单独说的行

### 1. `SUBMIT_MIN_RATIO = 1e18` 是「合规范围内的砖化」

两层都只查 `≤ 1e18`，而 `1e18` 本身就让门槛等于全员票权：只有持有 100% 票权的人能提交。这不是漏洞（参数在合法域内），但它是**唯一一个「合规但让机制失效」的取值**。部署时应当把它当区间而非上界看。

### 2. 两层「三层皆无」

- `NFT-03`：`MemberNFT` 的指数上界，纯算术、一次性，是唯一值得加链上 `require` 的地方；
- `DEP-01`：`init` 时序，抢跑窗口由 `--slow` 逐笔广播造成。

## 攻击者能插入什么

| 时点 | 动作 | 影响 |
| --- | --- | --- |
| 部署交易进 mempool 后 | 抢跑任一 `init` | 该合约永久绑定攻击者参数（`DEP-01`） |
| 部署完成后 | 无 | 所有参数不可变 |
| 运行期 | 无 | 没有 setter |

## 结论落在哪个不变量

> **「能让一个已正确部署的实例永久失效」的参数组合，必须至少有一层在广播前拦住。**

对 11 个组合成立，对 2 个不成立（`NFT-03`、`DEP-01`）。注意这个不变量的措辞是「已正确部署」——它把「部署脚本被绕过」排除在外，而 `DEP-01` 恰恰是「部署脚本本身被打断」，所以它绕过了这个前提，必须独立登记。

## 判定

| 项 | 结论 |
| --- | --- |
| 参数能否让协议永久不可用 | **能**，但 11/13 的组合在广播前被拒 |
| 哪些组合「三层皆无」 | `NFT-03`（指数上界）、`DEP-01`（`init` 时序） |
| 链上 require 是否值得加 | 只有 `MemberNFT` 的指数上界值得（一次性、纯算术、零运行期成本）；其余加链上校验只是复制广播前的检查，增加部署失败点 |
| `SUBMIT_MIN_RATIO = 1e18` | 参数在合法域内但机制失效；部署时应按区间而非上界看待 |
