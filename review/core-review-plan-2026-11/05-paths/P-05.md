# P-05 · 时间轴被放大

**路径**：`Phase.sync:86` → `Submit:319` → `Vote:76` → `Mint._isRoundEnded:100` → `Stake:790` / `Stake:231`

**固定三问**：状态修改顺序有无可利用窗口 / 攻击者能在哪个时点插入什么 / 结论落在哪个不变量。

## 时间轴表

设阶段 P 的 `sync` 把下一段长度定为 `B'`（`Phase:120-121`）。

| 相对时刻 | `block.number` | `phaseBlocks` | `currentPhase()` | 各模块读到的 round |
| --- | --- | --- | --- | --- |
| P 内任一时刻 | `n` | `B`（不变） | `P`（不变） | 全部模块读 `P` |
| P 的 `sync` 之后 | `n` | `B`（`_phaseBlocks(P)` 仍是旧段） | `P` | 仍是 `P` |
| P+1 的第一块 | `start(P)+B` | `B'` | `P+1` | 全部模块跳到 `P+1` |
| P+1 结束时 | `start(P)+B+B'` | `B'` | `P+2` | `P+2` |

关键：**`sync` 只写「下一段」，`currentPhase` 在同一笔交易内不跳变**。`_recordNextSegment:151-160` 把新段的起点算成 `previous.startBlock + (phase − previous.phase + 1) × phaseBlocks`，正好是 `phase+1` 的边界；`phaseAtBlock:65-71` 用 `nearest(startBlock)` 查段，所以 `block < start(P+1)` 永远落在旧段。

测试 `test_phaseBlocksHasNoUpperClamp` 断言了这一点：`phaseInfo(4).phaseBlocks == 1,001,000` 而 `phaseInfo(3).phaseBlocks == 1000`。

## 放大之后各模块怎么变形

| 模块 | 读什么 | `phaseBlocks` 放大 `k` 倍后 |
| --- | --- | --- |
| `Stake.withdraw:235` | `round > unlockRequestPhase + promisedWaitingPhases` | 等待期从「N 个阶段」变成「N × k 个阶段」的墙钟时间。`promisedWaitingPhases` 是阶段数，不随时间轴缩放 |
| `Stake._settleFees:791` | `_lastSettlePhase == round` | 每个阶段只能结算一次 → 结算频率降到 1/k |
| `Mint._prepareRewardIfNeeded:110` | `currentPhase() > round` | 「轮已结束」被推迟 k 倍 → 奖励发放延迟 |
| `Vote.vote:76` | `currentRound()` | 投票窗口变长 k 倍（更宽松，不是风险） |
| `Submit.submitNewProposal` | 同 | 每轮容量 1000 摊到更长的时间 → 提案密度下降 |
| `Phase` 自身的下一次调整 | `block.number − obs > phaseBlocks` | 阈值同步放大 k 倍 → 下一次调整要等 k 倍久，**自我锁定** |

反向（`phaseBlocks` 缩到 1）：每个块一个阶段 → 所有「每轮一次」的机制变成「每块一次」；`Stake` 的等待期变成「N 个块」，`Mint` 每块都能结束一轮。这会让 `_settleFees` 每块尝试一次、`_prepareRewardIfNeeded` 每块预留一次，gas 与事件密度暴涨。

## 攻击者能插入什么

| 角色 | 能影响 | 不能影响 |
| --- | --- | --- |
| 首个 `sync` 调用者（通常是当轮首个提交者，`Submit:319-322`） | 观测**时刻**（窗口起点） | 窗口内的块数/秒数比 |
| 出块者 | 时间戳（`elapsedSeconds`） | 观测时刻的选择（除非同时抢首推） |
| 任何人 | 直接调 `sync()` 抢在自己想要的时刻 | 时间戳 |

所以「放大」需要 `elapsedSeconds ≪ elapsedBlocks × 正常出块间隔`。同一块内所有交易共享时间戳，交易排序造不出这个比例。

## 结论落在哪个不变量

> **时间轴调整只能影响未来，不能改变当前轮次。**

成立（见时间轴表）。这一条是 `Phase` 设计里最扎实的部分：段起点向前对齐到阶段边界，使得任何 `sync` 都不会让正在进行的轮次提前结束或跳过。

第二条不变量**不成立**：

> ~~`phaseBlocks` 单次调整有上界~~

`Phase:120` 只把 0 钳到 1，没有上界；`ADJUST_THRESHOLD` 只决定「是否调整」，不决定「调多少」。见 `PHS-01`。

## 判定

| 项 | 结论 |
| --- | --- |
| 同一笔交易内轮次跳变 | **不可达**。新段从 `phase+1` 起 |
| 轮长被放大 100× | **机制上可达，实际需要时间戳异常**（`PHS-01`） |
| 放大后谁受损 | 全部依赖 phase 的时序：等待期、结算频率、奖励发放延迟。没有任何一方能单方面修复 |
| 采样点被操纵 | **只能抖动，不能定向**。观测时刻与时间戳同源，选择起点不改变比例 |
| 无提案的社区 | **不产生观测**（只有 `Submit` 与手动调用会触发 `sync`）→ 阶段长度冻结在最后一次观测的值 |

**一句话**：时间轴的正确性靠「段起点对齐阶段边界」这一条，它成立；时间轴的**稳定性**没有上界保护，它依赖一个隐含假设——出块间隔不会出现剧烈异常。
