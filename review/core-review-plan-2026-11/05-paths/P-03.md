# P-03 · 推举 → 回调 → 融合 / 投票

**路径**：`Submit.submitNewProposal:105` → `_submitByProposalId:277` → `_callProposalCreated:326` → `Stake.mergeStake:269` → `_hasUsedStakeRights:495` / `Vote.vote:69`

**固定三问**：状态修改顺序有无可利用窗口 / 攻击者能在哪个时点插入什么 / 结论落在哪个不变量。

## 回调内可达的写入口

| 入口 | 前置判据 | 结果 |
| --- | --- | --- |
| `Stake.mergeStake(token, source=自己, target=他人)` | `Stake:286` `_hasUsedStakeRights` → 读 `Submit.proposalIdBySubmitterId` | **revert `StakeRightsUsed`**（本轮已提交） |
| `Stake.mergeStake(token, source=他人, target=自己)` | 需要他人的 NFT 授权 | 与回调无关，正常转账逻辑 |
| `Stake.unstake` | 同上 `_hasUsedStakeRights` | **revert `StakeRightsUsed`** |

| `Submit.submitNewProposal(另一个自己拥有的 memberId)` | 该 id 本轮未提交 | 允许，最多到 `SUBMIT_ROUND_LIMIT` |
| `Mint.mintGovReward` | `_isRoundEnded` 为假 | **revert `RoundNotEnded`** |
| `Launch.launchToken` | 需要发射额度 | 允许，与提案无关 |

## 逐步序列（攻击者视角）

目标：在同一轮内「推举 + 投票 + 融合后再次推举」，把同一份份额的票权用两次。

| 步 | 动作 | 结果 |
| --- | --- | --- |
| 1 | `stakeLiquidity` 建仓，票权 `v` | 成功 |
| 2 | `submitNewProposal` 推举提案 A | 成功，`_submitInfoBySubmitterId[round][me] = A` |
| 3 | `onProposalCreated` 内（若是 Callback target）调 `mergeStake(me → other)` | **revert `StakeRightsUsed(token, round, me)`** |
| 4 | 退出回调，调 `vote(A, v)` | 成功，`voteAmountByMemberId[round][me] = v` |
| 5 | 再次 `unstake` / `mergeStake(me → 他人)` | **revert `StakeRightsUsed`**（`Stake:191`） |
| 6 | 让 target 侧成员把份额融合给自己，再推举一次 | 需要对方的 NFT 授权；且 `targetId` 的提交记录独立 → 这是**自愿的份额转让**，不是复用 |

第 3 步的 revert 选择器在测试里被完整断言（`test_mergeInsideProposalCreatedIsBlockedByWrittenState` 比较的是 `abi.encodeWithSelector(StakeRightsUsed.selector, token, round, botId)`，含三个参数）；同一成员在下一轮执行同一次 merge 成功，作为对照。

## 攻击者能插入什么

| 时点 | 动作 | 影响 |
| --- | --- | --- |
| 自己的提交前 | 无（门槛是活的，可被他人抬升——见 STK-01） | 提交可能被前一块的 `stakeBoost` 挡掉 |
| 回调内 | `stakeLiquidity` / `stakeBoost` | 抬高自己的票权；因为 `voteLimit` 每次重读，之后投票可用更多 |
| 回调内 | `vote` | 同一轮、同一提案，受累计上限约束 |
| 他人提交的回调内 | 只能改自己的状态（target 由**提案作者**指定） | 无法触及第三方 |

## 结论落在哪个不变量

> **「本轮已使用票权」这个事实必须先于任何回调写入状态**，否则回调可以绕过它。

`Submit:305-307` 与 `Vote:256-259` 都满足。`Stake._hasUsedStakeRights:495-502` 同时查两条（投过票 / 提交过），任何一条非零即锁。

## 判定

| 项 | 结论 |
| --- | --- |
| 同轮「推举 + 投票 + 融合 + 再推举」 | **不可利用**。融合的 source 侧在回调内外都被 `StakeRightsUsed` 挡住 |
| 目标已投票仍可接收融合（票权放大器） | **不成立**。target 接收融合只增加 target 的票权，且投票时 `voteLimit` 重读——这是「份额转让」，需要 target 的 NFT 持有人同意，不是绕过 |
| 回调内 `stakeBoost` 抬高嵌套 `vote` 的上限 | **允许但无收益**。抬的是自己的票权，且 `_vote` 用同一个 `voteLimit` 做累计校验（`Vote:250-254`），不会超发 |
| 回调内达到「半写状态」 | **不可达**。三处回调都在写完之后 |

**一句话**：这条路径的安全性来自一条纪律——**先写「已用票权」，再回调**。`Vote` 和 `Submit` 都遵守，`Stake` 的三处检查都读这两张表。
