# P-02 · 结算与换币

**路径**：`_settleFees:775` → `_realizeFees:812` → `_swap:853` → Router

**固定三问**：状态修改顺序有无可利用窗口 / 攻击者能在哪个时点插入什么 / 结论落在哪个不变量。

## 状态顺序

```
Stake:778  _reserves(pair)                              ← 读储备
Stake:779-784  reclassify → 写回 lastFee/Withdrawable/sqrtK
Stake:786  settlementUnit = W · ratio / 1e18
Stake:787  if (feeLp < settlementUnit) return           ← 门槛用 feeLp
Stake:791  if (_lastSettlePhase == round) return        ← 每 phase 一次
Stake:794  if (!_canBurn(settlementUnit)) return        ← 两侧都能出整数
Stake:818  _lastSettlePhase = round                     ← 先置位
Stake:820  _push(pair, pair, processedFeeLp)            ← LP 送进 pair
Stake:821  pair.burn(this)                              ← 拿到两种币
Stake:827  swap 父币 → 社区币
Stake:831  token.burn(总量)                             ← 烧
Stake:835  totals.lastFeeLp -= processedFeeLp           ← 最后改账
```

`_lastSettlePhase` 在外部调用**之前**写入，所以嵌套结算在 `:791` 就被挡住。剩下的「调用后才写」只有 `:835` 一处：如果 `_realizeFees` 在 `:820-831` 之间被重入，账本仍显示 `lastFeeLp` 未扣，而 LP 已经离开合约。这条重入路径不可达（`STK-03`：三条转账都无钩子），但顺序本身是反的。

## 攻击者能插入什么

| 时点 | 动作 | 影响 |
| --- | --- | --- |
| 上一块 | 在 pair 上买入社区币，推高价格 | 结算的 `amountOutMin` 在同一笔内现算（`:862-863`），会接受被推高的价 |
| 结算所在块 | 无（同一块内 `getAmountsOut` 与 `swap` 之间储备不变） | `amountOutMin` 恰好等于实际输出，永不因滑点 revert |
| 下一块 | 卖回 | 赚取价差 |

`amountOutMin = getAmountsOut(...)`（`:862-863`）的真实作用不是防滑点，而是**保证结算永不因价格失败**——它把「滑点保护」换成了「不可阻断」。跨块夹子的防线因此完全落在参数上。

## 获利不等式

先算清楚一件事：**夹一笔卖出，盈亏平衡点恰好是池费率**。

设池子父币储备 `P`、攻击者前置换入 `x`、受害者（这里是结算）卖出 `y`，忽略手续费时攻击者的净利润是

```
profit(x) = x(x + 2y)/P  −  0.006·x
```

（`0.006x` 是往返两次 0.3% 的手续费。）对 `x` 求极值后令 `profit = 0`，以 `u = y/P` 代入得到

```
u² − 2f·u + f² = 0 ,  f = 0.003   ⇒  (u − f)² = 0
```

**双重根在 `u = f`**，即：夹子只在「受害者这笔交易超过储备的 0.3%（= 池费率）」时才有正收益，恰好等于费率时收益为零（二阶）。

单次结算的卖出量

```
x = (settlementUnit / TS) · R_p = ratio · (W / TS) · R_p  ≤  ratio · R_p
```

（`W ≤ TS` 恒成立：`Stake` 持有的 LP 不超过 pair 总供应。）代入门槛 `x < 0.003·R_p`：

| `FEE_SETTLEMENT_RATIO` | 单次卖出量上界 | 夹子判定 |
| --- | --- | --- |
| `2.5e15`（0.25%，部署值） | `0.25% R_p` | **不可夹**，安全边际 1.2× |
| `3e15`（0.3%） | `0.3% R_p` | 临界（收益为零） |
| `6e15`（0.6%） | `0.6% R_p` | **可夹**，收益 ≈ `0.0009 R_p` |
| `1e16`（1%） | `1% R_p` | **可夹**，收益 ≈ `0.0049 R_p` |
| `1e17`（10%） | `10% R_p` | **可夹**，收益 ≈ `0.0094 R_p` |
| `1e18`（100%） | `100% R_p` | **可夹**，等于把整个池子的深度交给夹子 |

安全边际只有 **1.2×**（0.25% vs 0.3%），不是「远低于」。这条参数没有冗余：把 `FEE_SETTLEMENT_RATIO` 提到 0.3% 就正好落在盈亏平衡点上，再高一点就可套利。

这正是 `DeployCore:173-177` 与 `21_check:487` 强制 `2.5e15` 的理由，`deploy_scripts_test.py:162-171` 还把两份常量钉在一起。注释里写的「must not exceed the pool fee」正是上面这个双根条件的口语版。

## 结论落在哪个不变量

> **单次结算的卖出量必须小于池费率**：`FEE_SETTLEMENT_RATIO < poolFee`。

`0.25% < 0.3%`，成立，但余量只有 1.2×。这条不变量的意义是：即使 `amountOutMin` 完全不起保护作用，结算本身也不构成可套利的价差来源。

## 判定

| 项 | 结论 |
| --- | --- |
| 同笔重入 | **不可利用**。`_lastSettlePhase` 先置位；三条转账无钩子 |
| 跨块夹子（部署参数） | **不可利用**。0.25% vs 0.3% 门槛，1.2× 余量 |
| 跨块夹子（误配 0.6% 以上） | **可利用**。收益 ≈ `(ratio − 0.3%)² × R_p`，承担者是该社区全体持有人（他们的手续费被低价换掉） |
| 结算被阻断 | **不可利用**。`amountOutMin` 现算，价格再差也能成交；`_canBurn` 只兜「会 revert」的情形 |
| 结算吞掉 Boost 押金 | **不可利用**。`burn` 的实参恒等于本轮刚收到的量（测试 `test_settlementNeverTouchesBoostBacking`） |

**一句话**：这条路径的安全性不在代码里，在 `FEE_SETTLEMENT_RATIO ≤ 0.25%` 这个部署常量上。它被两处脚本 + 一处测试钉住，是本轮看到的少数「参数即安全边界」且真的被强制的地方。
