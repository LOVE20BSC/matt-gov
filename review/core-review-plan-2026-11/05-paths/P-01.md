# P-01 · 首存与存入通胀

**路径**：`Launch._createToken:250-260` → `Stake.stakeLiquidity:106` → `_addLiquidity:626` → `pair.mint` → `_creditLiquidity:578` → `_reclassify:671`

**固定三问**：状态修改顺序有无可利用窗口 / 攻击者能在哪个时点插入什么 / 结论落在哪个不变量。

## 状态顺序

```
Stake:637  _reserves(pair)                     ← 读储备（存储值，不含未 sync 的捐赠）
Stake:638  totals.lastFeeLp/withdrawableLp/sqrtK = _reclassify(...)   ← 先把 W 校准
Stake:640  added.withdrawableLpBefore = totals.lastWithdrawableLp     ← 定价基准
Stake:642  _optimalAmounts(...)                ← 按当前储备比例定实际用量
Stake:646-649  pull 用户两种币 → push 给 pair  ← 外部转账
Stake:651  added.lpMinted = pair.mint(this)    ← V2 按余额差计额
Stake:589-591  shares = S·lpMinted/W_before    ← 记份额
Stake:599  totals.lastWithdrawableLp += lpMinted
Stake:603  _updateSqrtKBaseline(...)           ← 重设基线
```

关键点：**份额是 `lpMinted` 的线性函数，而 `lpMinted` 由 V2 按真实余额差计算**。因此「份额价格被抬高」不能直接偷钱：抬高储备会让同一笔存款铸出更少的 LP，也会让 `shares` 同比例变少，两者抵消。

## 攻击者能插入什么

| 时点 | 可插入的动作 | 对受害者的影响 | 攻击者的净收益 |
| --- | --- | --- | --- |
| 受害者存款前 | 向 pair 转币（捐赠） | 提高 `sqrt(k)` → `_reclassify` 把 W 压小；同时抬高储备 | **零**：W 与 `lpMinted` 同比例缩小，`shares` 不变（见下） |
| 受害者存款前 | 在 pair 上 swap 推价 | 受害者按被推高的比例存入 → 相当于以高价买入 | 正，需满足下面的不等式 |
| 受害者存款前 | `sync` 把待计入的捐赠落账 | 同第一行 | 零 |
| 受害者存款后 | 无 | — | — |

### 捐赠路径为什么是零收益

设捐赠使 `sqrt(k)` 变为原来的 `f` 倍（`f = sqrt(1+Δ/R)`）。则

```
W_before' = W_before / f          （_reclassify:689）
lpMinted' = a_t·TS/(R_t+Δ)        （V2 按余额差）
shares'   = S·lpMinted'/W_before' = S·a_t·TS·f / ((R_t+Δ)·W)
          = S·a_t·TS / (R_t·f·W)  （因 f/(R_t+Δ) = 1/(R_t·f)）
```

`f > 1` → `shares' < shares`。受害者拿到**更少**的份额，但每一个份额对应的池子价值也同比例更高，索取权仍等于其出资额（`S6` 的恒等式）。攻击者为此付出的捐赠大部分进了待销毁账户（`STK-04` 的守恒证明）。

### swap 路径的获利不等式

存款与「买入」不同：存款是按池子当前比例注入两种币，**不改变价格**，所以受害者的损失不是一次性的价差，而是价格回落后才显现的无常损失。设攻击者前置换币量为 `x`、池子储备 `R`、价格被推离 `ε ≈ 2x/R` 倍，则

```
受害者损失 ≈ a_t · ε²/2        （无常损失 IL ≈ (Δp/p)²/8，再乘 2 次方向）
攻击者成本 ≈ 0.006 · x = 0.003 · ε · R
```

获利条件：

```
a_t · ε²/2 > 0.003 · ε · R   ⇔   a_t · ε > 0.006 · R
```

取 `ε = 0.1`（前置换币 = 储备的 5%）时需要 `a_t > 6% · R`；取 `ε = 1`（前置换币 = 储备的一半，已是极端操纵）时需要 `a_t > 0.6% · R`。

**结论**：存入夹子的收益是价格的二阶量，成本是一阶量，所以它需要「受害者存款相对池子很大」且「攻击者把价格推得很远」两个条件同时成立。对普通存款不成立，对大额首存成立。

## 结论落在哪个不变量

> **存款人的 LP 索取权恒等于其出资额**：`V(shares) = shares/(S+shares)·(W+L) = L`。

这条恒等式对任意 `W`、`S`、`f` 都成立（`S6` 的推导），与池子价格无关。所以「首存通胀」在本实现里不成立——它偷不到份额。

## 判定

| 项 | 结论 |
| --- | --- |
| 首存（空池） | **不可利用**。`_optimalAmounts:701-703` 单侧为 0 时返回原始数量、跳过滑点，对首存正是正确行为；`pair.mint` 的 `MINIMUM_LIQUIDITY = 1000` 保证第一个存款人拿到 `sqrt(a0·a1) − 1000`，无法用 1 wei 建仓 |
| 捐赠后存入 | **不可利用**。份额与 LP 同比例缩放，索取权不变；捐赠者自损 |
| 推价后存入 | **条件性可利用，且取决于受害者的 `slippage` 参数**。`_checkSlippage:716-723` 只比较「用户给的两个数量」与「按池子比例算出的最优量」，**不参照任何外部价格**。`slippage = 0` 且数量比取自推价前的池子 → 差额必然 > 0 → revert，攻击失败；`slippage = 1e18`（本仓所有测试用例的取值）→ 无任何保护 |
| 预建 Pair（H-01） | **不可利用**。见 `LCH-01`：复用后第一次 `pair.mint` 正常初始化，预先转入的父币成为第一个存款人的赠礼 |

**一句话**：这条路径的安全性完全落在 `slippage` 参数上，而仓库里所有示例与测试都用 `1e18`。集成方若照抄示例，存款就是一笔无保护的市价单。
