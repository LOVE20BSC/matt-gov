# 通用规则

## 主体与权限

- 业务主键为 MemberNFT 的 `memberId`；`author`、`submitterId`、`voterId` 均记录该身份，钱包地址仅作控制者或调用者。
- 处分成员资产、权益或业务状态时校验 `MemberNFT.ownerOf(memberId) == msg.sender`。单向融合只增加目标状态，不要求调用者持有目标 NFT。
- NFT 转移不改写历史质押、投票、发射、快照、已结算激励或事件。当前质押、未铸造激励、未用发射次数和解锁提取权由新持有人控制，解锁倒计时不重置。
- Proposal Target 和首批代币 distributor 是明确的地址型角色；群聊委托属于 Group Chat 内部权限，见 [组织上下文](../../../CONTEXT.md)。

例：Phase 10 申请解锁，等待 5 个 Phase；Phase 12 转移 NFT，仍在 Phase 15 由新持有人提取。

## 编号与精度

- Phase、治理 Round 和 MemberNFT 从 `1` 开始；`0` 表示未设置或无效。
- Proposal ID 由 Submit 单调分配并保持稳定，不把某个起始值用作通用哨兵。
- 比例一般采用 `1e18` 精度；名字带 `PerThousand` 的参数按模块公式使用千分比，不能混算。
- 金额比例分配默认向下取整；发射阈值及明确标为 `ceil` 的式子向上取整。

## 初始化与安全

- 一次性依赖初始化入口统一为 `init`，一律不设调用者限制；合约不保存部署者地址，也不授予部署者特权。成功后依赖地址和初始化参数不可替换，无升级管理员或协议级后门。
- 初始化状态只由 `init` 维护：`initialized` 初值为 `false`，首次成功调用后置为 `true`，再次调用回滚 `AlreadyInitialized()`；其他写入口不重复校验 `initialized`，未成功初始化的版本不会发布，其失败由各自的权限、参数与存在性校验决定。
- `init` 的检查顺序为先参数校验、后初始化状态；参数非法与重复初始化同时命中时按参数错误回滚。
- 部署与初始化分开的交易存在被抢先绑定的窗口：部署是否成功由发布前检查脚本核对实际绑定结果判定，逐项核对 `initialized()`、依赖地址和全部初始化常量，任何不一致即重新部署，不能把“部署后立即初始化”当作防抢跑保证。
- 写操作遵循检查、更新、交互顺序并防重入；失败不能留下半完成状态。

## 编号约束

Proposal ID 从 `1` 开始递增，`0` 永远无效；未创建对象使用显式存在性判断，不把真实业务记录编码为 `0`。
