# LOVE20BSC Compatibility 规格

状态：BSC 版实现前冻结的测试规格。

本文档定义 `compatibility` 代码库如何验证 BSC 外部依赖能否安全用于 `core` 和 `action`。该仓库只生成测试夹具、测试结果和证据，不部署或提供 LOVE20 生产合约，也不作为任何生产合约的运行时依赖。

## 1. 范围与非目标

测试对象分为两组：

1. 本地 Uniswap V2/WETH9 参考实现，用于建立可重复的行为和数值基线；
2. BSC 目标网络上的 WBNB、PancakeSwap Factory、Pair 和 Router，用于验证实际部署版本。

兼容的含义是 `Stake` 所需的接口、状态变化和数值计算结果可正确工作，不要求 PancakeSwap 与 Uniswap V2 源码逐字相同。手续费常量、权限、初始化和其他无关实现差异必须记录；只要差异会改变协议依赖的结果，就判定为不兼容，不能直接进入部署配置。

本仓库不修改外部合约，不替代生产适配层，不保存私钥，不执行真实用户资金操作，也不负责验证完整 PancakeSwap 产品功能。

## 2. 测试配置

每个目标网络使用独立 profile，至少包括：

- `anvil`；
- `bsc97_dev`；
- `bsc56_public_test`；
- `bsc56_public`；

其中 `bsc56_public_test` 是主网公测实例，`bsc56_public` 是主网正式实例；两个 chain ID 均为 `56`，必须使用完全独立的地址、配置、代币符号和前端环境。

profile 必须记录链 ID、RPC 标识、目标区块高度、WBNB 地址、Factory 地址、Router 地址，以及测试使用的 Pair 地址或创建参数。地址必须来自已验证的部署清单；未通过本规格的地址不得被 `core`、`action` 或 `script` 引用。

本地参考实现固定记录源码版本、编译器版本、优化器配置和部署区块。目标网络还必须记录合约地址、runtime bytecode 摘要、验证源码链接（如有）和测试执行提交。

## 3. 参考行为

参考夹具至少包含 WETH9 兼容封装代币、ERC20 测试代币、Uniswap V2 Factory、Pair 和 Router。测试数据应覆盖：

- 原生代币存入、取回和余额变化；
- `token0`/`token1` 顺序、Pair 创建和重复创建；
- LP 铸造、转移、销毁、`totalSupply` 和储备变化；
- Swap 手续费、输出数量、`k` 值变化和滑点边界；
- Router 报价与实际兑换输出；
- 数量不足、路径错误、滑点保护和权限错误时的回滚。

所有金额、储备、手续费和 `sqrt(k)` 计算均使用整数结果保存，明确向下取整或协议规定的舍入方式。

## 4. 外部合约兼容性

### 4.1 WBNB/WETH9

验证目标封装代币是否支持 `deposit`、`withdraw`、余额和原生代币转账语义，并与参考实现比较：

- 存入后 ERC20 余额增加、原生余额减少；
- 取回后 ERC20 余额减少、原生余额增加；
- 非法金额和余额不足时回滚；
- `Stake` 依赖的转账、授权和余额读取结果一致。

### 4.2 Factory、Pair 和 Router

逐项调用并记录参考值与目标值：

- Factory 的 `getPair`、`createPair`、Pair 地址唯一性和排序；
- Pair 的 `token0`、`token1`、`getReserves`、`totalSupply`、`mint`、`burn`、`swap`；
- Router 的 `getAmountsOut`、`swapExactTokensForTokens`、路径校验和 `amountOutMin` 语义；
- LP 份额、储备、手续费和兑换输出的状态变化；
- 失败调用的回滚和状态不变性。

不得仅以 ABI 能够编译或静态函数选择器一致作为通过条件。PancakeSwap 版本可能使用不同的手续费公式或其他 fork 差异，必须以目标地址的实际行为为准。

## 5. Stake 场景回放

兼容性结论必须包含 `Stake` 使用场景，而非只测试 DEX 单体接口。至少回放：

1. 用社区代币和父币加入 Pair，取得 LP 并读取份额；
2. 发生交易后再次读取储备、LP 供应量和 `sqrt(k)`；
3. 计算并结算 `feeLp`，验证社区代币销毁和父币经 Router 换成社区代币后销毁；
4. 检查 `withdrawableLp`、`totalLpShares`、成员 `lpShares` 和按份额提取结果；
5. 对 Pair、Router、销毁或滑点保护失败执行回滚测试。

参考实现与目标网络的差异只有在不影响上述结果时才可接受；影响结果时必须停止直接接入并记录待实现的适配方案。

## 6. 证据与判定

每次测试至少输出：

- profile、链 ID、目标合约地址和测试区块高度；
- 本地参考实现版本与目标 runtime bytecode 摘要；
- 调用名称、输入、返回值、事件、状态前后储备和供应量；
- 手续费、兑换报价、实际输出、`sqrt(k)` 和舍入差异；
- 交易哈希或本地测试标识、执行提交和失败原因。

测试结果分为：

- **通过**：所有 `Stake` 依赖的接口、行为和数值结果满足参考约束；
- **有记录的差异**：存在不影响协议结果的实现差异，并已记录版本和证据；
- **阻断**：接口缺失、状态/数值不一致、回滚语义不一致或证据不足。

只有“通过”或“有记录的差异” profile 才能被部署脚本采用；“阻断” profile 不得写入 BSC 地址配置。

## 7. 仓库边界

`core` 和 `action` 只能依赖经过验证的外部地址和接口定义，不导入 `compatibility` 的测试代码。`compatibility` 可以复制最小参考接口和夹具，但不得反向修改业务规格；外部地址、测试证据和结果变更应在本仓库与部署配置提交中同步记录。

## 8. 验收场景

至少覆盖两个 BSC profile 与本地参考实现的完整对照、Pair 创建和 LP 铸造/销毁、Swap 手续费与储备变化、Router 报价和实际输出、Token 顺序、失败回滚、`sqrt(k)` 计算，以及 `Stake` 加入、手续费结算、销毁和提取的成功与失败路径。
