# LOVE20BSC 协议概览

## 1. 协议定位

LOVE20 是一个**基于可验证的共识行动的铸币协议**。它让任何人可以为自己关心的共识创建代币，并通过持续的治理参与和共识行动来铸造激励，形成可持续的社群经济。

### 核心理念

**从空投到持续铸币**：
- 传统代币：预挖 → 空投 → 流通 → 死亡
- LOVE20：启动 → 治理 → 共识行动 → 持续铸造 → 自我循环

**关键差异**：
- 供应不是一次性分配，而是按 Round 持续铸造
- 激励不是被动持有，而是通过可验证的共识行动铸造
- 社群不是松散持币者，而是基于共识的行动网络

**什么是共识行动**：
- 不是为别人完成任务，而是为自己的共识而行动
- 例如：读书（个人成长共识）、运动（身体健康共识）、提供流动性（市场流动性共识）
- 行动基于链上规则可验证，不依赖主观评价

### 三层结构

```
┌─────────────────────────────────────┐
│     代币树（Token Tree）              │
│  首个代币 ← WBNB                      │
│     ↓                                │
│  子币 A、子币 B、子币 C...            │
└─────────────────────────────────────┘
           ↓
┌─────────────────────────────────────┐
│     治理层（Governance）              │
│  质押 → 投票 → 激励                   │
│  Phase 推进 → Round 循环             │
└─────────────────────────────────────┘
           ↓
┌─────────────────────────────────────┐
│     行动层（Action）                  │
│  LP 行动、链群行动、链群服务          │
│  参与 → 验证 → 铸币                   │
└─────────────────────────────────────┘
           ↓
┌─────────────────────────────────────┐
│     群聊层（Group Chat）              │
│  代币社区 Chat、治理 Chat             │
│  行动 Chat、链群 Chat                │
└─────────────────────────────────────┘
```

## 2. 核心机制

### 2.1 统一身份：MemberNFT

**为什么需要**：
- 钱包地址会转让、会丢失，不适合作为长期身份
- 需要一个可转让但历史不变的身份载体

**如何运作**：
- 每个参与者铸造一个 MemberNFT（`memberId` 从 1 开始）
- 所有状态（质押、投票、发射次数、行动参与）都关联 `memberId`
- NFT 转移时，新持有人继承未铸造的权益，但不能改写历史

**典型场景**：
- Alice 用钱包 A 铸造 MemberNFT #100
- Alice 质押、投票，获得治理激励份额
- Alice 将 MemberNFT #100 转给 Bob
- Bob 可以领取 Alice 尚未铸造的激励
- Bob 不能修改 Alice 的投票历史

---

### 2.2 时间轴：Phase 与 Round

**为什么需要**：
- 协议需要时间分片来组织治理和行动
- 需要动态适应区块时间波动

**Phase 设计**：
- Phase 是底层时间基础设施，只提供连续的无语义时间片
- 不命名 Vote、Join、Verify、Mint 等业务阶段
- 动态校准：观测实际区块时间，调整 Phase 长度使其接近目标天数

**Round 映射**：
- Core 治理层：Phase N = 治理 Round N（一对一）
- Action 行动层：各 Executor 自行映射（LP 3 阶段，链群 4 阶段）

**典型流程**：
```
Phase 1: 治理 Round 1 投票
Phase 2: 治理 Round 2 投票 + Round 1 可以加入 LP/链群行动
Phase 3: 治理 Round 3 投票 + Round 2 加入 + Round 1 LP 铸币
Phase 4: 治理 Round 4 投票 + Round 3 加入 + Round 2 验证 + Round 1 链群铸币
...稳态运行
```

---

### 2.3 治理循环

**为什么需要**：
- 代币供应受 `maxSupply` 限制，需要持续铸造机制
- 需要激励社群持续参与治理而非一次性空投后死亡

**如何运作**：

**1. 质押阶段**（任何时候）
```
成员 → 质押 LP（流动性质押）→ 获得治理票
     → 质押代币（加速质押）→ 不产生治理票，但参与加速激励分配
```

**2. 投票阶段**（Phase N）
```
成员 → 创建 Proposal → 推举 → 投票
          ↓
      治理票权重决定投票权
```

**3. 铸币阶段**（Phase N+1）
```
准备 Round N 激励池：
  govReward = available × GOV_RATIO
  proposalReward = available × PROPOSAL_RATIO

治理激励拆分：
  - 50% 投票激励：按实际投票权重分配
  - 50% 加速激励：按加速质押份额分配，上限为投票激励的 2 倍

Proposal 激励：
  - 达到门槛的 Proposal 按投票权重分配
  - 铸给 Proposal Target（行动由 ActionTarget 分发）
```

**为什么拆分投票和加速激励**：
- 只奖励投票：成员可能只质押不投票（搭便车）
- 只奖励质押：失去投票激励，治理参与度降低
- 拆分 50%/50%：平衡投票积极性和资金锁定激励
- 2 倍上限：防止纯加速质押而不投票的极端情况

---

### 2.4 共识行动激励

**为什么需要**：
- 社群不能只投票，需要可验证的共识行动
- 行动可以是为自己（读书、运动、个人成长），也可以是为社群（提供流动性、组织社群、提供服务）
- 共识行动需要激励才能持续

**三类行动**：

**LP 行动**：
- 共识：为代币提供流动性，促进市场流通
- 参与：加入 Round 内质押 LP
- 验证：基于链上 LP 数量和时间自动验证
- 铸币：按有效 LP 占比分配，受治理票上限约束
- 时间权重：越早加入权重越高（防止最后时刻涌入）

**链群行动**：
- 共识：成员组织自己的社群完成共识行动（如读书会、运动打卡、技能学习）
- 参与：成员加入链群，链群 owner 组织协作
- 验证：公共验证者基于链上规则确定行动得分
- 铸币：链群按得分占比分配 → 成员按个人得分分配

**链群服务行动**：
- 共识：为链群行动提供公共服务（如验证服务）
- 参与：成员作为验证者服务多个链群行动
- 验证：复用链群行动的验证结果，不重复验证
- 铸币：按服务的链群行动规模聚合计算
- 二次分配：链群 owner 可以将自己的 owner 部分激励分配给其他贡献者（验证者部分不参与二次分配）

---

### 2.5 群聊与资格

**为什么需要**：
- 社群需要交流场所
- 不同身份需要不同权限的群聊空间

**五类 Chat**：

| 类型 | 谁能发言 | 典型用途 |
|------|---------|---------|
| 代币社区 Chat | 持币者 or 有治理票 or 参与行动 | 全社区广场 |
| 代币治理 Chat | 有治理票 | 治理讨论 |
| 代币行动 Chat | 投票支持该行动 or 参与该行动 | 行动协调 |
| 代币行动治理 Chat | 投票支持该行动 | 行动治理决策 |
| 链群 Chat | 群管理员加入 or 参与该链群行动 | 社群内部协作 |

**资格动态性**：
- 持币资格：实时查询余额
- 治理票资格：实时查询质押状态
- 行动投票资格：查询最近 RECENT_ROUNDS 轮投票记录
- 行动参与资格：查询 ActionTarget 登记
- 链群归属资格：查询链群 Executor 的 17 组索引

## 3. 完整用户旅程

### 3.1 成为社区成员

```
1. Alice 铸造 MemberNFT #100（支付少量首个代币作为铸造费）
2. Alice 获得代币（从 Airdrop 领取、购买或通过共识行动铸造）
3. Alice 现在可以发言（代币社区 Chat）
```

### 3.2 参与治理

```
1. Alice 质押 LP（代币 + WBNB）到 Stake 合约
2. Alice 获得治理票（lpShares × promisedWaitingPhases）
3. Alice 可以在代币治理 Chat 发言
4. Alice 对多个 Proposal 投票（同一 Round 可多次投票）
5. 下一 Round，Alice 铸造治理激励：
   - 投票激励：按她的投票权重占比
   - 加速激励：如果她还质押了代币，按加速份额占比（上限 2 倍投票激励）
```

### 3.3 参与 LP 行动

```
1. Bob 创建 LP 行动 Proposal（设置 govRatioMultiplier = 2e18）
2. Alice 投票支持该 Proposal
3. Proposal 获得足够票数，进入下一 Round 的加入阶段
4. Alice 在加入阶段质押 LP 到该行动
5. 再下一 Round，Alice 铸造 LP 行动激励：
   effectiveRatio = min(
     她的有效 LP 占比（经时间权重扣减）,
     她的治理票占比 × 2  // govRatioMultiplier
   )
   她铸造的激励 = proposalReward × effectiveRatio
```

### 3.4 参与链群行动

```
1. Carol 创建链群行动 Proposal（例如：每日读书打卡共识行动，验证规则：最近 7 天读书天数）
2. 社区投票支持，Proposal 达到阈值后每轮都有激励
3. Dave 用自己的 MemberNFT #200 创建链群并激活链群 Chat
4. Dave 组织自己的社群，Alice、Bob 投票支持链群行动后可以加入
5. Alice、Bob 在链群内协作（链群 Chat 沟通），持续完成每日读书行动
6. 验证阶段（每轮独立）：公共验证者基于链上规则（最近 7 天读书天数）确定：
   - Alice 本轮行动得分 60 分（7 天读了 6 天）
   - Bob 本轮行动得分 40 分（7 天读了 4 天）
7. 铸币阶段（每轮独立）：
   - Dave 的链群本轮铸造激励 = proposalReward × 链群得分 / 总得分
   - Alice 本轮铸造 = 链群激励 × 60 / 100
   - Bob 本轮铸造 = 链群激励 × 40 / 100
8. 下一轮重复验证和铸造，只要 Proposal 激励池有余额
```

### 3.5 提供链群服务

```
1. Eve 创建链群服务 Proposal（面向整个社区的所有链群行动）
2. Eve 作为公共验证者，服务多个链群行动的验证
3. 铸币阶段：
   - Eve 铸造验证者激励 = Σ(每个行动的验证者部分激励)
   - 如果 Eve 同时是某链群 owner，还铸造 owner 部分激励
4. Eve 可以配置二次分配，将自己的 owner 部分激励分配给其他贡献者
   （验证者部分不参与二次分配）
```

## 4. 关键设计权衡

### 4.1 为什么使用 MemberNFT 而非钱包地址？

**钱包地址的问题**：
- 不可转让：私钥一旦泄露，所有历史和权益无法迁移
- 无法交易：无法将"社区成员身份"作为资产出售
- 难以继承：钱包持有人去世，身份无法传递

**MemberNFT 的优势**：
- 可转让：NFT 转移后，新持有人继承未铸造权益
- 可交易：社区身份本身成为有价值资产
- 历史不变：转移不改写投票记录，保护治理公正性

### 4.2 为什么 Phase 不命名业务阶段？

**固定命名的问题**：
- 不同行动类型需要不同阶段（LP 3 阶段，链群 4 阶段）
- 未来可能需要 5 阶段、6 阶段的新行动类型
- 底层 Phase 改变会影响所有上层业务

**无语义 Phase 的优势**：
- 底层只提供时间分片，不关心上层如何解释
- 各 Executor 自行映射 Phase 到业务 Round
- 扩展性：新行动类型自由定义阶段模型

### 4.3 为什么 ActionTarget 不直接分配激励？

**直接分配的问题**：
- 不同行动类型激励逻辑完全不同（LP 时间权重、链群验证、服务聚合）
- ActionTarget 无法预知所有未来行动类型
- 耦合度高，扩展困难

**Executor 模式的优势**：
- ActionTarget 只负责统一接口和参与登记
- Executor 专注各自的业务逻辑
- 新行动类型只需实现新 Executor，不改 Core

### 4.4 为什么链群服务要复用链群行动的验证？

**独立验证的问题**：
- 重复验证浪费 gas 和时间
- 验证结果可能不一致（同一成员在两次验证中结果不同）
- 链群服务的价值本身来自于它服务的链群行动

**复用验证的优势**：
- 一次验证，多处使用
- 权重数据来源一致（都基于链群行动的验证数据）
- 阶段自然对齐（服务在 Phase p+3 铸币，行动在 Phase p+2 验证完成）

## 5. 激励流动路径

```
┌─────────────────────────────────────┐
│  maxSupply - totalSupply            │  可用供应
└──────────────┬──────────────────────┘
               │
               ├──────────────────┐
               ↓                  ↓
        ┌─────────────┐    ┌─────────────┐
        │ govReward   │    │proposalReward│
        │  (50%)      │    │   (50%)      │
        └──────┬──────┘    └──────┬───────┘
               │                  │
        ┌──────┴──────┐           │
        ↓             ↓           │
   ┌────────┐   ┌────────┐       │
   │投票激励│   │加速激励│       │
   │ (25%)  │   │ (25%)  │       │
   └────┬───┘   └────┬───┘       │
        │            │            │
        ↓            ↓            ↓
    按投票权重  按加速份额   达到门槛的
    铸造给投票  铸造给投票   Proposal Target
    的成员      的成员       (ActionTarget)
                                 │
                    ┌────────────┼────────────┐
                    ↓            ↓            ↓
                ┌───────┐   ┌────────┐  ┌─────────┐
                │LP行动 │   │链群行动│  │链群服务 │
                │Executor│  │Executor│  │Executor │
                └───┬───┘   └────┬───┘  └────┬────┘
                    │            │           │
                    ↓            ↓           ↓
              按有效LP占比  链群→成员    验证者+owner
              铸造给参与者  按得分铸造   按服务权重铸造
```
              分配给参与者  按贡献分配   按服务权重
```
