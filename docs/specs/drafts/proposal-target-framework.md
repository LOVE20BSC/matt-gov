# 如何设计 Proposal Target 框架

> 开发草案，依据现行 Core 与 Action 规格。

**提案框架**是一类提案共用的业务规则。Core 管理提案、推举、投票和提案激励铸造。框架通过 **Target** 接入 Core，由 **Executor** 处理参与、验证和成员结算等具体工作。

Action 通过 `ActionTarget` 接入 Core。

| 行动 | 提案绑定的 Executor |
| --- | --- |
| 链群行动 | `GroupActionExecutor` |
| 链群服务 | `GroupServiceExecutor` |
| LP 行动 | `LpExecutor` |

## 接入 Core

1. 创建提案时，把 `ActionTarget` 地址写入 `target`，将 `targetMode` 设为 `Callback`。Core 同笔创建并推举新提案，依次触发创建和推举回调。Core 以 `(tokenAddress, proposalId)` 识别提案，行动沿用该 `proposalId` 作为 `actionId`。 [Core 提案规格](../core/05-submit.md)
2. `ActionTarget` 实现 `IProposalTarget`。创建数据填 `abi.encodePacked(executorAddress, executorData)`，其中 `executorData` 按所选 Executor 的约定编码。ActionTarget 读取前 20 字节的 Executor 地址，确认它是合约并验证 `ACTION_TARGET_ADDRESS()` 指向自己，然后固定提案绑定。地址后的数据原样交给 Executor 校验与保存。 [ActionTarget 规格](../action/01-action-target.md)
3. 创建和推举回调验证调用者为 `Submit`，投票回调验证调用者为 `Vote`。Target 按已存绑定转发当次推举或投票的数据，Executor 确认调用者是自己绑定的 Target。首次推举和后续推举都可以各自传入数据。投票回调收到的是本次新增票数，链群行动可据此累计指定给验证者申请的票。回调失败时，触发它的 Core 交易整体回滚。 [Core 回调约定](../core/01-common-rules.md)

每个提案绑定一个 Executor。链群行动提案和链群服务提案各有自己的票数和激励预算。查询或结算已有提案时，使用 Core 记录的 Target 和该 Target 为提案记录的 Executor。

## 用 Core 的阶段划分行动轮

`N` 是这批行动记录对应的治理轮编号。参与、验证和结算都继续使用 `N` 记账。框架读取 Core 的 `Phase`，按下表安排各环节。提案创建后的下一阶段起，可以开始加入。

| Core 阶段 | 链群行动与链群服务 | LP 行动 |
| --- | --- | --- |
| `N` | 推举、投票。链群行动的投票可指定验证者申请。 | 推举、投票。 |
| `N+1` | 链群行动成员加入、追加或退出。符合资格的链群 owner 和验证者可加入链群服务。 | 存入、追加或撤回指定流动性凭证。 |
| `N+2` | 链群行动验证并登记来源结果。链群服务复用这些结果，链群 owner 可在此阶段设定二次分配。 | 轮次开放结算。 |
| `N+3` 起 | 链群行动和链群服务开放结算。 | 已开放的轮次可以继续结算。 |

例如第 **10** 轮在第 **11** 阶段加入，第 **12** 阶段可结算 LP 行动，也正是链群行动的验证阶段。第 **13** 阶段起可结算两类链群提案。加入阶段结束后固定该轮参与记录，验证阶段结束后固定该轮链群验证记录。历史结算继续引用原轮次。 [行动轮次规格](../action/02-phase-model.md)

加入轮共用 `ActionRoundAxis`。各 Executor 根据自己的轮次规则校验成员操作和最早结算阶段，并核对业务资格。

## Executor 分工

提案绑定的 Executor 向 Target 写入通用的加入和退出登记。具体参与量、资产、验证结果和成员结算由对应 Executor 保存。 [参与规格](../action/03-participation.md)

### 链群行动与链群服务

- **`GroupActionExecutor`** 管链群激活、成员参与、验证者选举和评分。在 `N+2` 可以通过 `actionReward` 读取 Core 为已结束的投票轮计算的额度。每项源行动在所有参与链群都完成验证、总得分和提案激励均为正时，登记本项额度，并累计到来源社区的当轮总额和验证者权重。成员按最终得分占全行动总分的比例获得激励。 [链群行动规格](../action/05-group-action-executor.md)
- **`GroupServiceExecutor`** 管链群 owner 和验证者的服务加入、服务激励与二次分配。它从绑定的 `GroupActionExecutor` 读取**指定来源社区、同一轮**的已登记结果。每个来源行动独立判断是否计入。验证阶段结束后，即使尚无来源行动成员领取，服务也可以结算。 [链群服务规格](../action/06-service-executor.md)

服务激励来自**服务提案自己的预算**。同轮源行动激励总额是分配分母，验证者按自己完成验证的源行动额度计权，链群 owner 按本链群在源行动中的激励份额计权。服务提案配置两个角色的预算比例。owner 部分再应用治理上限及当轮适用的二次分配配置。

### LP 行动

**`LpExecutor`** 校验和托管提案指定的流动性凭证，记录每轮存入、撤回和时间扣减。加入结束后，用该成员的有效数量占全体有效数量的比例分配该提案激励。启用治理上限时，按领取时的治理权计算上限并销毁超出部分。 [LP 行动规格](../action/04-lp-executor.md)

## 结算与资金流向

1. **成员向 Executor 结算。** 身份 NFT 的当前持有人指定提案和轮次。Executor 校验该轮处于提案创建轮与当前已开放的结算轮之间，成员尚未结算，并满足有效参与量、验证结果或服务权重等业务条件。
2. **Core 为该提案该轮整笔铸造一次。** 有效的首次成员结算中，Executor 通过 `ActionTarget` 请求 `Mint.mintProposalReward`。`ActionTarget` 确认调用者是该提案绑定的 Executor，并核对提案的当轮投票状态。Core 校验登记的 Target、已结束的投票轮、激励门槛及铸造状态，再把该提案的整笔激励直接铸给绑定的 Executor。Core 按 `(tokenAddress, proposalId, round)` 去重。 [Core Mint 规格](../core/07-mint.md)
3. **Executor 按成员分配。** 后续有效领取走已铸造余额，每笔按 `(tokenAddress, proposalId, round, memberId)` 记账。转账付给各收款身份 NFT 的当前持有人。转账和销毁总额受该提案该轮已铸造额度约束。若本次应付和应销毁金额都为零，或转账失败，交易整体回滚。达标但缺少有效参与或完整验证的行动，整笔激励保持预留状态。 [行动铸造规格](../action/07-minting.md)

以第 10 轮为例，假设以下提案均达标、治理上限关闭、链群 owner 的份额全部自留。金额以代币最小单位计。

| 提案 | 条件与结算示例 |
| --- | --- |
| LP 行动 | 第 12 阶段起结算。激励为 60，成员有效数量为 50，全体有效数量为 200，成员领取 `60 × 50 ÷ 200 = 15`。 |
| 链群行动 | 第 13 阶段起结算。激励为 100，所有参与链群已完成验证，成员最终得分为 30，总分为 100，成员领取 `100 × 30 ÷ 100 = 30`。 |
| 链群服务 | 第 13 阶段起结算。服务激励为 50，验证者比例为 20%。当轮只有上面一项来源行动，验证者权重为 100，某链群 owner 权重为 60。若两人都在当轮加入服务，验证者领取 `50 × 20% × 100 ÷ 100 = 10`，owner 领取 `50 × 80% × 60 ÷ 100 = 24`。 |

## 评审时走一遍的场景

- 通过 Core 创建三种行动提案，检查 `ActionTarget` 将回调转给各自绑定的 Executor。Executor 的 Target 地址校验失败时，创建交易回滚。
- 对第 10 轮，在第 12 阶段验证 LP 可结算，链群行动可登记来源额度，链群两类结算仍会被拒绝。在第 13 阶段用已验证且尚无成员领取的源行动，验证服务可以结算。
- 两位成员依次领取同一提案同一轮，Core 只整笔铸造一次，各成员只结算一次。若首次领取中的转账失败，恢复到此前的铸造与领取状态。
