# LOVE20BSC 全文档审查指南

本指南用于审查 `matt-gov` 当前所有组织约束、协议规格、迁移记录和验收文档。目标不是润色文字，而是确认：实现者只读目标规格即可实现，部署者可以按文档启动，测试者可以据此判定通过或失败，且不同文档不会给出两套规则。

## 一、审查原则

1. **先确定权威，再看内容**：`CONTEXT.md` 和 `docs/specification-structure.md` 定义边界；`docs/specs/<repo>/` 的拆分文件定义协议；`CHANGES-*` 和 `.scratch/` 只解释来源与决策。
2. **代码优先于旧文档**：旧仓库代码用于验证“保留逻辑”是否真实存在；它不能覆盖 BSC 当前规格。
3. **规格必须自包含**：实现者不应为了理解 BSC 规则而阅读旧仓库；旧代码引用只能作为行为证据。
4. **每个结论可验收**：禁止只写“合理”“适当”“按需”“通常”；必须能转成输入、状态变化、输出或 revert 条件。
5. **先审不变量，再审接口**：先确认资产、权限、时间、供应和历史是否守恒，再检查函数是否能表达这些规则。
6. **不为历史兼容增加复杂度**：BSC 是独立代际；旧地址、存储和历史状态不属于本轮实现要求。

## 二、审查范围与权威层级

### 必审文件

**组织约束**

- `CONTEXT.md`
- `docs/repositories.md`
- `docs/specification-structure.md`
- `docs/acceptance.md`

**协议规格**

- `docs/specs/core/README.md` 及 `core/00` 至 `core/08`
- `docs/specs/action/README.md` 及 `action/00` 至 `action/08`
- `docs/specs/group-chat/README.md` 及 `group-chat/00` 至 `group-chat/08`
- `docs/specs/compatibility.md`

**迁移与变更说明**

- `docs/specs/CHANGES-core.md`
- `docs/specs/CHANGES-action.md`
- `docs/specs/CHANGES-group-chat.md`

### 追溯文件

- `.scratch/bsc-protocol-migration/map.md`
- `.scratch/bsc-protocol-migration/issues/*.md`

追溯文件用于解释决策，不得成为实现规则的唯一来源。若追溯票据与当前拆分规格冲突，以当前拆分规格为准，并记录冲突。

## 三、审查前准备

在报告开头记录：

- 审查提交：`git -C matt-gov rev-parse HEAD`
- 审查日期和审查人
- 文件清单及行数：`rg --files matt-gov/docs matt-gov/.scratch | sort`
- 是否存在未提交修改：`git -C matt-gov status --short`
- 当前目录结构是否符合 `docs/specification-structure.md`

快速发现断链和旧入口：

```sh
rg -n 'core\.md|action\.md|group-chat\.md|launchFirstToken|initializeGenesis|TODO|TBD|待定|未明确' matt-gov --glob '*.md'
```

审查过程中不要修改旧 `LOVE20TKM` 仓库。需要验证旧逻辑时，只记录仓库、提交、文件路径、函数名和行号。

## 四、四轮审查流程

### 第一轮：结构和入口（文档级）

- [ ] 每个必审文件都在清单中
- [ ] README 链接都指向当前存在的拆分文件
- [ ] 被删除或迁移的文件没有继续作为规范入口
- [ ] 每个协议代码库都有明确的 `README.md`、模块文件和 testing 文件
- [ ] 目录结构、文件名、编号和导航表一致
- [ ] 迁移规则、当前存放位置和迁移后位置一致
- [ ] 没有同一规则的第二份可编辑副本

输出一张“文档地图”：每个文件的职责、上游来源、下游引用和权威级别。

### 第二轮：逐文件内容审查

每个文件按以下顺序检查，并在报告中引用具体行号。

#### 1. 范围

- [ ] 明确本文件负责什么
- [ ] 明确不负责什么
- [ ] 未把其他代码库的职责偷偷写入本文件

#### 2. 术语

- [ ] 与 `CONTEXT.md` 完全一致
- [ ] `memberId`、`tokenAddress`、`proposalId`、`actionId`、`groupId`、`round`、`phase` 没有混用
- [ ] `Phase` 与业务 `Round` 明确区分
- [ ] 首次出现的缩写和外部协议名称已定义

#### 3. 状态模型

- [ ] 每个状态字段有类型、键、初始值和生命周期
- [ ] 状态转换写明前置状态、触发者、动作和后置状态
- [ ] 当前状态与历史快照的边界明确
- [ ] NFT 转移、解锁、退出、销毁和失败回滚后的状态明确

#### 4. 接口

- [ ] 每个公开函数有完整 Solidity 签名
- [ ] 参数、返回值、可见性、权限、事件和错误均有说明
- [ ] 只读查询说明空值、越界、未开始和不存在对象的行为
- [ ] 数组、批量参数和分页参数有最大边界

#### 5. 数学和单位

- [ ] 每个变量的单位、精度和分母已定义
- [ ] 向上取整、向下取整、余数和溢出处理明确
- [ ] 除数为零、供应量为零和总量为零均有规则
- [ ] 公式示例与公式本身一致

#### 6. 失败原子性

- [ ] 外部调用失败是否全部回滚
- [ ] 批量操作任一项失败是否整体回滚
- [ ] 更新、交互顺序是否避免重入和半完成状态
- [ ] 失败后是否不会留下已扣余额、已记次数或错误索引

#### 7. 验收

- [ ] 每个关键流程至少有成功、边界、失败三个场景
- [ ] 场景包含输入、前置状态、操作、预期事件/状态和判定命令
- [ ] 测试要求没有只写“覆盖充分”或“通过测试”

### 第三轮：跨文档一致性

建立以下矩阵，逐项打勾：

| 主题 | 必须互相一致的文件 | 核查内容 |
| --- | --- | --- |
| 身份 | `CONTEXT.md`、Core、Action、Group Chat | 业务主体是否始终是 `memberId` |
| 时间 | `CONTEXT.md`、`core/03`、`action/02`、Group Chat Query | Phase、治理 Round、ActionRound 是否可推导且不冲突 |
| 回调 | `core/05`、`core/06`、`action/01`、CHANGES | 签名、参数顺序、KV、失败回滚是否一致 |
| 激励 | `core/06`、`action/07`、`acceptance.md` | 预留、铸造、销毁和分配是否守恒 |
| 发射 | `core/00`、`core/07`、`acceptance.md`、CHANGES | `Launch.init`、首币、次数和阈值是否一致 |
| 参与 | `action/01`、`action/03`、Group Chat 类型 | 登记、forceExit、资产和资格来源是否一致 |
| 群聊身份 | `CONTEXT.md`、Group Chat 全部模块 | owner、delegate、sender、admin 是否都按 NFT 身份运行 |
| 仓库边界 | `repositories.md`、各 README、规格依赖 | 是否存在越界 import、循环依赖或运行时依赖误标 |
| 验收 | `acceptance.md`、各 testing 文件、CHANGES | 每个承诺是否都有测试和证据位置 |

发现冲突时，必须记录两份原文、冲突影响和唯一修订方向。

### 第四轮：可实现性与证据

选择至少三条真实流程，尝试只根据当前规格写伪代码：

1. `MemberNFT.mint` → 费用计算 → NFT 铸造；
2. `Vote` → `prepareRewardIfNeeded` → 治理/Proposal 激励铸造；
3. `Launch.init` → 首个代币 → Pair → Airdrop；
4. 一条 Action 加入/退出/验证/铸造流程；
5. 一条 Group Chat 发言和黑名单流程。

每条流程都检查：

- [ ] 不需要猜测缺失参数
- [ ] 不需要阅读旧代码才能决定 BSC 行为
- [ ] 能写出成功和失败断言
- [ ] 能确定事件和状态差异
- [ ] 能确定部署顺序和外部地址来源

伪代码无法落地的位置就是规格缺口，至少标为 P1。

## 五、协议专项检查

### Core

- [ ] MemberNFT ID 从 `1` 开始且不复用
- [ ] NFT 转移只改变当前控制者，不回写历史
- [ ] Stake 的 LP 与加速质押不产生 SL/ST 凭证
- [ ] 解锁申请、等待期、提取和融合的权限及资产变化闭合
- [ ] `Phase` 的生成、观测、校准和历史不可回写
- [ ] Submit/Vote 的主体、门槛、增量投票和回调一致
- [ ] `rewardReserved` 每轮只增加一次
- [ ] `rewardReserved >= rewardMinted + rewardBurned`
- [ ] `eligibleProposalVotes` 的维护、冻结和零值处理明确
- [ ] Proposal 激励分母只包含达标 Proposal
- [ ] Launch 上限优先于阈值判断，`threshold == 0` 不除零
- [ ] `Launch.init` 同时完成依赖绑定和首个代币部署
- [ ] TokenFactory 只能由 Launch 调用

### Action

- [ ] `ActionTarget` 只负责映射、回调、通用登记和 forceExit
- [ ] `executor` KV 的键、编码、位置和代码检查固定
- [ ] `proposalId == actionId` 的别名边界清楚
- [ ] LP、Group Action、Service 的阶段映射分别可推导
- [ ] 加入、追加、体验资产、部分撤回、退出的账本互不抵扣
- [ ] Group Action 17 组索引的加入、删除、最后关系清理闭合
- [ ] Round 历史的懒继承不会把退出状态错误继承
- [ ] 候选排名、分割线、批次游标和永久锁定规则可执行
- [ ] 验证不完整时行动层激励为零，底层 Proposal 激励仍可独立处理
- [ ] Service 只复用已完成验证的 Group Action，聚合范围和代币关系明确
- [ ] 全量扫描、批量铸造和二次分配有可执行边界

### Group Chat

- [ ] 一个 MemberNFT 只能对应一个 Chat
- [ ] `senderId`、owner、delegate、admin 全部按 MemberNFT 校验
- [ ] 不存在默认 NFT 映射和地址主体接口
- [ ] owner/delegate 的资格绕过范围明确，admin 不会意外绕过黑名单
- [ ] scope → ban → before → 写入 → 事件 → after 的顺序固定
- [ ] `beforePost` 失败回滚，`afterPost` 失败保留消息并记录错误
- [ ] 消息、提及、引用、分页和 Round 索引的边界明确
- [ ] 五类 Chat 的资格和黑名单权重来源逐一对应
- [ ] Group Action 归属资格与 ActionTarget.forceExit 的差异明确
- [ ] 黑名单双阈值、撤票、刷新和权重快照可复现

### Compatibility

- [ ] 每个目标 profile 有独立地址、区块、代码摘要和提交
- [ ] WBNB、Factory、Pair、Router 均有真实调用结果
- [ ] 记录 token 顺序、储备、供应、手续费、报价和舍入
- [ ] 覆盖 Pair 创建、LP 铸造/销毁、Swap、滑点和失败回滚
- [ ] 包含 Stake 加入、手续费结算、销毁和提取场景
- [ ] 未验证 profile 不会进入部署配置
- [ ] 测试仓库不成为生产合约运行时依赖

## 六、迁移与旧代码引用审查

### 迁移矩阵

对每个旧组件检查：

- [ ] 旧仓库和路径存在
- [ ] 来源提交已固定
- [ ] 新状态是保留、重构、修改、删除或新增之一
- [ ] 新位置明确
- [ ] CHANGES 与当前拆分规格一致
- [ ] 删除项没有在当前规格重新出现

引用格式统一为：

```text
LOVE20TKM/<repo>@<commit>:<path>#<function-or-symbol>
```

只有无法访问或尚未固定提交的引用，才标为“需人工验证”。不要接受只有文件名、模糊仓库目录或过大的行号范围。

### 组织边界

- [ ] `LOVE20TKM` 只读约束在迁移流程、脚本和验收中一致
- [ ] 旧组织地址、存储和历史状态没有被误写成 BSC 运行时依赖
- [ ] Burn 的 Airdrop 仅作为外部 distributor，来源、部署和地址证据明确
- [ ] `interface-test` 是前端开发入口，`interface` 只在验收后人工同步
- [ ] `launch` 未被错误创建为独立代码库

## 七、安全、经济和可运维性审查

### 权限

- [ ] 每个写接口只有一个明确权限来源
- [ ] NFT 转移后权限实时读取 owner，不缓存旧地址
- [ ] 回调、TokenFactory、Launch、Executor 的调用链不能被旁路
- [ ] 外部合约地址检查非零、代码存在和初始化完成

### 资金与供应

- [ ] 所有代币转移前后余额守恒
- [ ] 供应上限、预留、铸造、销毁不会重复计算
- [ ] LP 手续费增量不会被错误分配给旧质押者
- [ ] 体验资产、二次分配和失败回滚不会锁死资金

### Gas 与可运维性

- [ ] 用户可控数组和集合有写入上限
- [ ] 历史扫描、Proposal 聚合和索引清理有界
- [ ] 批量接口记录最大成功规模和首次失败规模
- [ ] 永久锁定、失联验证者和 forceExit 等不可逆取舍有运维说明

## 八、问题分级与放行门槛

### P0：阻塞

- 权威入口冲突，导致实现者可能写出两种行为
- 核心接口、权限或部署顺序缺失
- 资金、供应或激励存在可重复领取、锁死或越权风险
- 关键公式或状态机无法实现

处理：停止实现，修规格并重审。

### P1：实现前必须修复

- 公式分母、零值、舍入或状态边界不完整
- 回调、事件、错误或批量边界缺失
- 跨文档术语、依赖或阶段映射不一致
- 伪代码需要猜测关键行为

处理：进入实现前修复；修复后至少重跑相关专项和跨文档审查。

### P2：不阻塞但应修复

- 旧引用不精确但不影响行为判断
- 示例、导航或事件字段说明不完整
- 重复解释、过时统计和格式问题

### P3：后续优化

- 可读性、排版、额外图示或非关键示例

## 九、审查报告格式

```markdown
# LOVE20BSC 文档审查报告

审查提交：<sha>
审查日期：<date>

## 结论
- 是否可以开始实现：是 / 否
- P0：N
- P1：N
- P2：N
- P3：N

## P0 / P1 问题
### [P1] <一句话标题>
- 文件：`docs/specs/core/06-mint.md:42`
- 证据：引用原文或公式
- 问题：说明两种解释或缺失条件
- 影响：指出会导致错误实现、部署失败或验收无法判定
- 建议：给出唯一可执行的修订方向

## 跨文档矩阵
| 主题 | 文件 | 结果 | 证据 |
| --- | --- | --- | --- |

## 旧代码引用清单
| 当前文件 | 旧引用 | 提交/路径 | 状态 |
| --- | --- | --- | --- |

## 放行条件
1. ...
2. ...
```

每个问题只描述一个根因；不要把多个问题合并成“文档不完整”。报告最后必须明确：可以开始实现，还是必须先修规格。

## 十、完成标准

全文档审查只有同时满足以下条件才算完成：

- [ ] 所有必审文件已逐文件检查
- [ ] 规范入口和链接无歧义、无断链
- [ ] 跨文档矩阵无未解释冲突
- [ ] 至少三条关键流程可仅按当前规格写出伪代码
- [ ] 所有 P0 已关闭
- [ ] 所有影响正确性的 P1 已关闭或明确阻塞实现
- [ ] 旧代码引用均可追溯或标记人工验证
- [ ] 验收场景有输入、断言和证据位置
- [ ] 报告中给出明确放行结论
