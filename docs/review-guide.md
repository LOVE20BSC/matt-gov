## 审核维度

### 1. 完整性（Completeness）

**接口定义**
- [ ] 所有公开函数是否有完整签名（函数名、参数、返回值、可见性）
- [ ] 状态变量是否定义清楚（类型、映射关系、初始值）
- [ ] 事件是否定义完整（事件名、参数、触发时机）
- [ ] 错误/revert 条件是否明确（错误名、触发条件）

**业务逻辑**
- [ ] 计算公式是否完整（包括单位、精度、舍入规则）
- [ ] 状态转换是否明确（从哪个状态到哪个状态，触发条件）
- [ ] 权限检查是否完整（谁能调用、如何验证权限）
- [ ] 边界条件是否覆盖（零值、最大值、空集合、未初始化）

**依赖关系**
- [ ] 外部依赖是否明确（依赖哪些合约、哪些接口）
- [ ] 跨仓库接口是否定义（回调、查询、事件订阅）
- [ ] 初始化顺序是否明确（哪个合约先部署、如何连接）

**验收标准**
- [ ] 每个关键功能是否有对应的验收场景
- [ ] 测试覆盖率要求是否明确
- [ ] 成功/失败的判定标准是否清晰

---

### 2. 清晰性（Clarity）

**术语一致性**
- [ ] 同一概念是否使用同一术语（不在不同地方换名）
- [ ] 术语是否在 CONTEXT.md 中有定义
- [ ] 缩写是否在首次出现时说明

**语义明确性**
- [ ] 避免模糊表述："适当的"、"合理的"、"尽可能"、"通常"
- [ ] 时间相关的描述是否明确（"立即"、"下一轮"、"最终"）
- [ ] 数量描述是否精确（"所有"、"至少一个"、"最多 N 个"）

**逻辑清晰**
- [ ] 条件分支是否穷尽（if-else 是否覆盖所有情况）
- [ ] 循环和批量操作的边界是否明确
- [ ] 原子性要求是否明确（哪些操作必须在一个交易中完成）

---

### 3. 一致性（Consistency）

**文档内部一致性**
- [ ] 同一文档不同章节的描述是否一致
- [ ] 接口定义与使用示例是否匹配
- [ ] 状态图与状态变量定义是否对应

**跨文档一致性**
- [ ] CONTEXT.md 的术语与各规格文档是否一致
- [ ] core.md 定义的回调接口与 action.md 实现是否匹配
- [ ] action.md 的查询接口与 group-chat.md 依赖是否对应
- [ ] repositories.md 的依赖关系与各规格的 import 是否一致

**与组织约束一致性**
- [ ] 是否遵守 CONTEXT.md 的主体模型（使用 memberId 而非地址）
- [ ] 是否遵守 repositories.md 的仓库边界（没有越界依赖）
- [ ] 是否遵守 CLAUDE.md 的迁移硬约束（LOVE20TKM 只读）

---

### 4. 正确性（Correctness）

**业务逻辑正确性**
- [ ] 公式是否正确（数学上、业务上）
- [ ] 状态转换是否合理（没有死锁、没有非法状态）
- [ ] 激励分配是否守恒（铸造总量 ≤ 可用供应）
- [ ] 权限模型是否安全（没有权限绕过、没有越权）

**数据结构正确性**
- [ ] 映射关系是否正确（key-value 对应关系）
- [ ] 索引是否完整（需要查询的维度是否都有索引）
- [ ] 枚举是否可行（大集合是否提供分页）

**边界条件正确性**
- [ ] 零值处理是否正确（0/0 除零、空数组、空字符串）
- [ ] 溢出处理是否正确（uint256 最大值、数组长度）
- [ ] 初始状态是否正确（未初始化时的默认行为）

**引用正确性**
- [ ] 引用旧代码位置是否正确（文件名、行号、函数名）
- [ ] 引用的旧逻辑是否真的保留（没有误引用已删除的逻辑）

---

### 5. 可实现性（Implementability）

**是否有足够信息实现**
- [ ] Agent 或开发者能否仅从规格文档实现代码
- [ ] 是否需要阅读旧代码才能理解（如果是，旧代码位置是否给出）
- [ ] 是否需要额外的领域知识（如果是，是否在文档中说明）

**是否有足够信息测试**
- [ ] 是否有清晰的输入-输出示例
- [ ] 是否有边界条件的测试场景
- [ ] 是否有失败场景的测试要求

**是否可部署**
- [ ] 初始化参数是否明确
- [ ] 部署顺序是否可行（没有循环依赖）
- [ ] 外部依赖的地址来源是否明确

---

### 6. 安全性（Security）

**权限控制**
- [ ] 每个状态修改操作是否有权限检查
- [ ] 权限检查是否完整（没有漏洞）
- [ ] 是否有防御重入攻击的措施

**资金安全**
- [ ] 代币转移是否有充足性检查
- [ ] 是否有防止资金锁定的机制
- [ ] 激励铸造是否有上限保护

**状态一致性**
- [ ] 失败时是否完全回滚（没有半完成状态）
- [ ] 并发操作是否安全（没有竞态条件）
- [ ] 外部调用失败是否正确处理

## 审核流程

### 第一遍：快速扫描（30分钟）
1. 阅读文档目录，理解整体结构
2. 扫描每个章节的标题和第一段
3. 标记出明显的问题（错别字、格式错误、明显矛盾）

### 第二遍：逐章审核（2-3小时）
1. 逐章仔细阅读
2. 对照审核维度检查
3. 记录发现的问题（位置、问题描述、严重程度）

### 第三遍：跨文档对照（1小时）
1. 检查跨文档一致性
2. 验证依赖关系是否对齐
3. 确认术语使用一致

### 第四遍：可实现性验证（30分钟）
1. 选择一个典型功能（如 MemberNFT.mint）
2. 尝试根据规格写出伪代码
3. 检查是否有遗漏的信息

## 问题严重程度分级

### P0（阻塞实现）
- 关键接口缺失或定义不完整
- 核心逻辑描述矛盾或缺失
- 安全漏洞（权限绕过、资金锁定）
- 跨文档严重不一致

**处理：必须立即修复，否则无法开始实现**

### P1（影响正确性）
- 公式错误或边界条件缺失
- 状态转换逻辑不清晰
- 验收标准缺失或不明确
- 术语不一致导致理解困难

**处理：应在实现前修复，否则可能导致返工**

### P2（影响效率）
- 描述冗余或啰嗦
- 示例不够清晰
- 引用旧代码位置不够精确
- 小的术语不一致

**处理：可以在实现过程中逐步修复**

### P3（改进建议）
- 格式优化
- 补充解释性注释
- 增加示例或图表

**处理：非阻塞，可以后续优化**

## CHANGES 文档的特殊审核要点

CHANGES 文档（CHANGES-core.md, CHANGES-action.md, CHANGES-group-chat.md）记录"为什么改"和"从哪里来"，是理解迁移决策和验证实现正确性的关键。

### 审核维度

#### 1. 迁移矩阵完整性
- [ ] 旧代码库的所有主要组件是否都在矩阵中
- [ ] 每个组件的状态是否明确（保留/重构/修改/删除/新增）
- [ ] 旧位置和新位置是否都填写完整
- [ ] 核心变化是否简洁说明

**检查方法**：
- 列出 LOVE20TKM 对应仓库的所有合约
- 逐一核对是否在迁移矩阵中有说明
- 标记遗漏的组件

#### 2. 旧代码引用正确性
- [ ] 引用的文件路径是否正确（相对于 LOVE20TKM 组织）
- [ ] 引用的行号范围是否合理（不要太大）
- [ ] 引用的描述是否匹配实际内容（需人工验证）

**引用格式检查**：
```
✅ 正确：`LOVE20TKM/group/contracts/LOVE20Group.sol` 78-95 行
⚠️ 可疑：`LOVE20Group.sol` 1-500 行（范围太大）
❌ 错误：`group/LOVE20Group.sol`（缺少 LOVE20TKM/ 前缀）
```

**输出要求**：
- 生成所有旧代码引用的清单
- 标记"需要人工验证"的引用（我们无法访问 LOVE20TKM）

#### 3. 与规格文档的一致性
- [ ] CHANGES 说"✅ 保留"的，规格文档是否也保留
- [ ] CHANGES 说"🔄 修改"的，规格文档是否体现了修改
- [ ] CHANGES 说"❌ 删除"的，规格文档是否确实没有
- [ ] CHANGES 说"➕ 新增"的，规格文档是否有完整定义

**检查方法**：
```
CHANGES-core.md 说：
  "✅ 保留逻辑：铸造费用公式"
  
检查 core.md 第 3.3 节：
  - [ ] 是否有铸造费用公式
  - [ ] 公式是否与 CHANGES 描述一致
  - [ ] 是否引用了同样的旧代码位置
```

#### 4. 迁移原则的贯彻
检查规格文档是否真的贯彻了 CHANGES 开头声明的迁移原则。

**Core 迁移原则**：
- [ ] 身份统一 — 规格中是否所有主体都用 memberId
- [ ] 去凭证化 — 规格中是否没有 SL/ST token
- [ ] 时间灵活 — 规格中是否使用 Phase 而非固定阶段
- [ ] 独立协议 — 规格中是否没有旧合约兼容性要求

**Action 迁移原则**：
- [ ] 身份统一 — 同上
- [ ] 时间灵活 — 是否使用 Phase 映射
- [ ] 职责分离 — ActionTarget 和 Executor 是否分离
- [ ] 单向转移 — 是否支持体验资产转移

#### 5. 删除声明的准确性
- [ ] 声明"不迁移"的组件，在规格文档中是否真的没有
- [ ] Out of scope 与 CHANGES 删除项是否一致
- [ ] 是否有组件在 CHANGES 中删除，但规格中又出现

**特别检查**：
- CHANGES 说 LP V1 不迁移 → action.md 是否只有 V2
- CHANGES 说 SL/ST 不迁移 → core.md 是否没有这些 token
- CHANGES 说 Burn 不迁移 → 但 Airdrop 作为外部依赖的描述是否清晰

### 模糊性问题
❌ "适当地处理"、"合理的范围"、"尽可能快"
✅ "检查 x > 0 后返回 y"、"最大 100 个元素"、"在同一交易中完成"

### 不完整问题
❌ "函数 foo(x) 返回结果"
✅ "函数 foo(uint256 x) external returns (uint256 result)"

### 不一致问题
❌ 第 3 章称为 "memberId"，第 5 章称为 "accountId"
✅ 全文统一使用 "memberId"
