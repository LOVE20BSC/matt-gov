# LOVE20BSC 代码迁移规范

本规范用于把 `LOVE20TKM` 代码迁移到新的 BSC 代码库。它服务于可审查性，不替代模块规格或 ABI 对账。

## 变更讨论原则

当前规格是阶段性参考，不是迁移讨论中不可推翻的标准。发现旧行为、当前规格和 BSC 目标之间不一致时，不应只因为“规格写过”就拒绝修改，也不应只因为“旧代码如此”就照搬。

每项变更按以下顺序判断：

1. 原始需求和 BSC 目标是否真的需要它；
2. 旧代码实际做了什么，哪些行为是必要不变量，哪些只是历史实现；
3. 新行为是否更合理、更安全、更容易实现或维护；
4. 变更的影响是否覆盖 ABI、权限、资产、事件、错误、历史和下游依赖。

确认决策后，再同步 `interfaces/`、模块规格和迁移对账文档。规格与实现暂时不一致，首先是待决策项，不自动判定为实现缺陷。

## 开工顺序

1. 固定旧仓库提交；旧仓库只读。
2. 完成三层 ABI 对账：函数、事件、错误、结构体和枚举都必须标记为保留、改名、改参、删除或新增。
3. 创建目标代码库最小骨架，先确认编译和跨仓库 import。
4. 一次只实现一个代码库、一个合约。

## 每个合约的提交结构

每个合约在目标代码库只保留两个提交：

1. **旧代码基线**：从固定旧提交复制原实现文件和接口文件；不带入已裁决删除的无关依赖，不做格式化或语义修改。
2. **BSC 实现**：在基线上完成该合约的全部 BSC 改造，并同步测试、README 或必要说明。

不要用额外的样式提交、临时修复提交或 revert 提交污染历史；发现问题时，在实现提交完成前 amend。已纳入 Git 的文件需要保留路径连续性；路径变化使用 `git mv`，不要删除后重建。

## 修改原则

- 保持旧代码的声明顺序、状态变量顺序、函数顺序和格式，除非 BSC 规格明确要求改变。
- 保留旧命名；只有协议语义明确变化时才改名。常量及其 getter 默认保持旧的大写命名。
- 先删除已裁决移出的业务和依赖，再补入 BSC 必需内容；不复制不会使用的旧合约、库或外部接口。
- Core 统一使用 `Proposal`；只有 Action 层使用 `actionId` 作为 Proposal 的业务别名。
- 接口以 `matt-gov/interfaces/` 为唯一 ABI 来源；目标仓库的 `src/interfaces/` 必须与之同步。
- 初始化是否需要权限按协议目标决定；去中心化模块可采用一次性无权限 `init`，但必须由发布前 check 脚本核验依赖和参数。

## 每一步的审查证据

开始修改前说明：本步目标、涉及接口、明确不改的内容和验证方式。提交前至少检查：

- 编译通过；
- ABI 与对账表一致；
- 成功、边界和失败回滚路径有测试或明确的最小验证；
- 旧行为的保留项没有无意变化；
- 工作树干净，提交只包含本步内容。

不得把“能编译”当作迁移完成；旧行为差异必须能追溯到当前规格或迁移决策。
